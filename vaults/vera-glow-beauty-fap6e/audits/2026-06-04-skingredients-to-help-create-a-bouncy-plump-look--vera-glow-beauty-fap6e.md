### 2. Link & Tracking Issues

**Braze opaque redirect wrapping**
All click-tracked URLs route through `links.elfcosmetics.com/f/a/wapQmtYq-23iHAqZgogTBg~~/.../` — Braze's standard hashed redirect format. The destination URL and any UTM parameters are encoded into the hash and cannot be verified from the HTML source. This is a process gap, not a rendering defect, but final-destination QA requires Braze click-report inspection or manual link expansion.

**Single visible CTA**
Only one trackable link is present in the truncated source (the hero image). If additional CTAs exist in the clipped portion, this is not a finding — but the audit cannot confirm full link coverage.

**Image asset domain**
Hero image is served from `braze-images.com` (Braze CDN):
```
https://braze-images.com/appboy/communication/assets/.../original.png?1698158310
```
The cache-busting query param (`?1698158310`) is a Unix timestamp from 2023, which is expected for immutable assets. No issue, but note the asset is not on elfcosmetics.com's own CDN.

---

### 3. Rendering & Accessibility

**Empty `<title>` tag**
```html
<title></title>
```
Samsung Mail and some preview panes render the `<title>` value. An empty title shows as a blank string or falls back to the subject line inconsistently. Populate with the subject or email name.

**Three consecutive empty `html_block` divs**
`block-2`, `block-3`, and `block-4` are structurally present but contain only whitespace:
```html
<div style="font-family:Open Sans,Arial,Sans-serif;text-align:center" align="center"> </div>
```
These add dead markup weight (~300 bytes) with no rendered output. Likely leftover from template scaffolding.

**Nested `nl-container` inside `html_block`**
The first `html_block` (block-1) contains a fully re-declared `nl-container > row > row-content > column` table tree — a complete nested email skeleton inside the outer skeleton. This suggests content was copy-pasted from another template or a Braze content block was embedded without stripping its wrapper. While this renders in most clients, it's technically invalid nesting and will cause unpredictable behavior in strict renderers.

**Image alt text is non-descriptive**
```html
alt="e.l.f." title="e.l.f."
```
The hero image links to a product page. The alt text identifies the brand but not the linked destination or image content. When images are blocked, subscribers see only "e.l.f." with no call-to-action context. WCAG 2.1 §1.1.1 requires alt text to convey the image's purpose when it is a link.

**No issues found:** Viewport meta is present; MSO conditionals are correctly applied; Google Fonts is gated behind `<!--[if !mso]>` to prevent Outlook download failure; `lang="en"` is set on `<html>`; responsive breakpoint at 640px uses correct `.stack .column` approach.
