### 3. Rendering & Accessibility

**Issue 1 — Invalid HTML comment syntax inside `<style>` block (confirmed).**
Two rules inside the `@media only screen and (max-width: 600px)` block are wrapped in HTML comment delimiters:

```css
<!-- *[class=contenttable] { width:414px !important;} -->
<!-- *[class=mobile] { width:414px !important;height: auto !important;} -->
```

HTML comments are not valid CSS. These rules will be silently dropped in all conformant CSS parsers. The `.contenttable` and `.mobile` mobile-width overrides are effectively dead code, meaning those elements will not reflow correctly at narrow viewports.

**Issue 2 — Triple-redundant font loading.**
Fonts are declared three ways simultaneously for the same families:
- `<link href="https://db.onlinewebfonts.com/...">` tags (stripped by Gmail, Outlook.com, Apple Mail iOS)
- `@import url(...)` inside the `<style>` block (also stripped by Gmail)
- `@font-face` declarations (the only mechanism with any email client support)

The `<link>` and `@import` entries add HTTP latency and will never render in the majority of inboxes. They should be removed.

**Issue 3 — Third-party CDN for licensed font assets.**
`BrownBold`, `BrownLight`, and `BrownThin` are served from `db.onlinewebfonts.com`, a public aggregator with no email infrastructure SLA. `BrownRegular` is correctly self-hosted at `www.drunkelephant.com/on/demandware.static/`. The CDN-hosted variants should be migrated to the same self-hosted path for reliability and licensing compliance.

**Issue 4 — `line-height: 100%` on `*` selector.**
The rule `*{line-height: 100%}` applies globally after the `ExternalClass` normalization block. This will collapse line-height on multi-line text cells in several Outlook versions where `mso-line-height-rule: exactly` compounds the effect.
