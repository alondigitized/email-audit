## Technical Audit

## 1. Technical Summary
The visible HTML is a table-based XHTML Transitional template built in Salesforce Marketing Cloud (SFMC/ExactTarget), with a CSS-checkbox hamburger nav. Only the `<head>` was available, so body-level links, footer and unsubscribe markup could not be verified. The QA run raised no hard failures, only 4 warnings, all of them header-capture or relay limitations.

## 2. Link & Tracking Issues
- **Unverified tracking links:** 30 tracking/click-redirect links were skipped because the HTTP probe doesn't cover redirect domains. Their destinations, status codes and redirect chains are unverified, and the truncated source doesn't show the domains.
- **Plain-text part is mostly URLs:** 5693 of 6520 characters (87%) are URLs, so the plain-text part is mostly long tracking redirects. That is a common spam-filter heuristic. It also means the text alternative is hard to read for text-only clients and screen-reader fallbacks.
- No broken links were confirmed.

## 3. Rendering & Accessibility
- **Zoom disabled:** `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">` blocks pinch-zoom on mobile. This fails WCAG 1.4.4 (Resize Text).
- **Invalid font stack:** `.disclaimerText { font-family: Arial, Helvetica, 'sans-serif'; }` quotes the generic family. A quoted `'sans-serif'` is read as a font name, not the generic fallback, so the stack has no true generic fallback.
- **Class selectors are brittle:** the mobile rules use exact-match attribute selectors such as `*[class=contenttable]`, `*[class=mobile]` and `*[class=hide]`. They stop matching if an element has more than one class, so responsive styles can silently fail.
- **Hamburger nav depends on `:checked`:** the nav uses `.navbar-checkbox:checked~.menu` inside `@media (max-width:600px)`. Gmail and most Outlook builds don't support this, and the truncated source doesn't show a fallback. Nav may be unusable in those clients.
- **Duplicate declaration:** `*[class].show` sets `width: auto !important` and then `width: 278px`. This is harmless but sloppy.
- **Legacy and non-standard CSS:** `.ReadMsgBody` and `-ms-text-size-adjust` are legacy. `-webkit-animation: bugfix` on `body` is a hack that can cause repaint issues.
- **Title has trailing whitespace:** `<title>Neiman Marcus </title>` is minor, and the title doesn't match the subject.
- **Image alt text and contrast:** both are unverifiable because the body was truncated.

## 4. Personalization & Merge Tokens
- **Internal template notes left in the source:** the top of the document has an unstripped HTML comment ahead of `<!DOCTYPE>`. It exposes SFMC variables and data-extension names: `NM_Subscriber_New_Consolidated`, `NM_CRM_Feed`, `@uEm`, `@cmdid`, `@base_refid`, and the line `SET @user = HASHED_EMAIL_SHA256`. This is a minor information disclosure, and the comment before the doctype can push some clients into quirks rendering.
- **Possible hashed-email identifier:** the comment suggests a hashed email (SHA-256) is used as an identifier. The truncated source doesn't show whether it appears in link URLs. If it does, it is a persistent identifier that gets forwarded with the email.
- No unresolved merge tokens (`%%…%%`, `{{…}}`) were found in the visible portion.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- **No List-Unsubscribe header:** the QA check didn't find one. It notes that the AgentMail relay may strip it, so treat this as unconfirmed.
- **No List-Unsubscribe-Post header (RFC 8058):** none was found, so one-click unsubscribe support is unconfirmed. Gmail and Yahoo bulk-sender rules require it. The same relay caveat applies.
- **Authentication-Results not captured:** SPF, DKIM and DMARC alignment for `e.neimanmarcus.com` is unknown because the relay doesn't expose the header.
- **Footer not visible:** the in-body unsubscribe link and the physical postal address required by CAN-SPAM are not in the truncated source and need checking in the full HTML.

## 6. Email-to-Site Continuity (UTM params, landing page alignment)
Not assessable from the data provided. The 30 tracking links were not resolved, so UTM parameters, `refid` handling, and landing page destinations are unconfirmed. The source suggests a `@refid` built from `@base_refid`, but its use in link URLs can't be confirmed.

## 7. Recommendations
1. **Zoom:** remove `maximum-scale=1` from the viewport meta.
2. **Template comment:** strip the SFMC variable comment block from the sent output, or move it below the doctype.
3. **Font stack:** change `'sans-serif'` to unquoted `sans-serif` in `.disclaimerText`.
4. **Responsive selectors:** switch `*[class=…]` to `[class~=…]` or `.class` selectors.
5. **Hamburger nav:** confirm a non-checkbox fallback exists for Gmail and Outlook.
6. **Unsubscribe headers:** verify `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` on the original message, not the relay copy.
7. **Authentication:** check SPF, DKIM and DMARC alignment against the raw message headers.
8. **Tracking links:** resolve a sample of the 30 tracking links to confirm final destinations and UTM/refid parameters. Run the audit on the full, untruncated HTML to cover the footer, alt text and unsubscribe link.
9. **Plain text:** shorten or simplify the plain-text part's URLs, for example by using fewer or cleaner links, to reduce the URL ratio.
