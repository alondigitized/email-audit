### 3. Rendering & Accessibility

**Issue 1 — Empty `<title>`**
```html
<title></title>
```
Some clients (Outlook on the web, older Android Gmail) surface the `<title>` value as a secondary preview. An empty tag renders as blank or "no subject" in those contexts.

**Issue 2 — Trailing comma creates an invalid CSS selector (dark mode block)**
```css
h1,h2,p,{color:#fff!important}
```
The trailing comma before `{` is invalid CSS. Strict-parsing clients (Apple Mail, recent Gmail) will drop the entire rule, leaving `h1`, `h2`, and `p` in their default (light-mode) colors in dark mode.

**Issue 3 — Misplaced semicolon breaks `!important` on anchor color**
```css
a{color:#fff;!important}
```
The semicolon terminates the `color` declaration before `!important`; `!important` is then parsed as a separate (invalid) declaration and discarded. The `#fff` value applies, but without `!important` it will lose specificity battles against more-specific light-mode rules when dark mode is active.

**Issue 4 — Possible unclosed `@media` block**
The `@media(prefers-color-scheme:dark)` block appears to close with `a .link{color:#fff!important}` immediately followed by `</style>` — with no closing `}` for the media query itself. If the full source confirms this, every rule after the opening `{` is scoped to dark mode only, which would corrupt light-mode rendering in affected clients. *Verify in full source.*

**Issue 5 — Duplicate `display:none` declaration**

Harmless but redundant; the first declaration is immediately overridden.
