### 3. Rendering & Accessibility

**Conflicting image `max-width` media queries (high confidence bug):**

```css
@media only screen and (min-width: 768px) { img { max-width: 600px } }  /* declared first */
@media only screen and (min-width: 640px) { img { max-width: 640px } }  /* declared second — wins via cascade */
```

On screens ≥768px both rules match; the 640px rule wins (later in source order), so desktop images cap at 640px rather than 600px. The intent appears reversed — the wider breakpoint should produce the narrower constraint. Result: images may overflow a 600px container on wide desktop clients.

**`maximum-scale=1` in viewport meta:**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```
Prevents user zoom in iOS Mail — accessibility regression, particularly for recipients with low vision.

**No dark mode CSS:**
```html
<meta name="color-scheme" content="light">
<meta name="supported-color-schemes" content="light">
```
Forces light rendering with no `@media (prefers-color-scheme: dark)` block. Apple Mail, Gmail iOS, and Outlook Mobile will attempt forced inversion, potentially inverting brand colors and making light text on dark backgrounds unreadable.

**Universal `line-height: 100%` in `*` selector:**
```css
*{ ... line-height: 100%; }
```
Collapses line height on multi-line copy to single-spaced. Any paragraph with two or more lines will have no leading. This should be scoped to single-line elements only.

**Duplicate `format-detection` meta tags:**
Three separate `format-detection` declarations — the combined one plus two individual ones for `date` and `address` and `telephone`. Harmless but indicative of template drift.

**Developer comment left in production output:**
```html

```
Typo (`IMPUT` → `INPUT`) and the placeholder itself should be removed before send. The following empty comment `<!---->` confirms no font was injected, which may be intentional but should be confirmed.
