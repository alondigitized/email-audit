### 3. Rendering & Accessibility

**Double-slash font paths (confirmed):**
Three `@font-face` declarations use double slashes in the CB2 origin path:
```
https://www.cb2.com//Styles/CB2/fonts/BrownLight/lineto-brown-light.woff2
https://www.cb2.com//Styles/CB2/fonts/BrownRegular/lineto-brown-regular.woff2
https://www.cb2.com//Styles/CB2/fonts/GTSectra/GT-Sectra-Display-Regular.woff2
```
Most servers normalize this via 301, but strict clients (some corporate proxies, older Outlook WebApp) may fail to load these resources. The single-slash declarations elsewhere in the same file confirm this is a copy-paste defect.

**Conflicting desktop media queries:**
Two separate `@media` blocks both target `img` max-width for desktop:
```css
@media only screen and (min-width: 690px) { img { max-width: 690px } }
@media only screen and (min-width: 768px) { img { max-width: 100% !important } }
```
On viewports ≥ 768px, the `!important` rule overrides the 690px cap and lets images render at full table width — likely unintended given the 690px cap exists. On 690–767px viewports, images are hard-capped at 690px with no override. The two rules are contradictory and should be collapsed into one.

**Mobile breakpoint targets a single device size:**
```css
@media only screen and (max-width: 418px) { .mobile { width:414px !important } }
```
This triggers only on ≤ 418px viewports, corresponding to iPhone SE/mini. Standard email mobile breakpoints use 600px. Android devices, iPad mini in portrait, and older iPhones in landscape will get neither the mobile nor the desktop layout — they'll render the table at whatever parent width the client assigns.

**`maximum-scale=1` blocks zoom:**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```
This prevents text zoom in iOS Safari. WCAG 1.4.4 requires text to be resizable up to 200% without assistive technology. Low-vision users are blocked from scaling the content.

**Link color near-invisible from body text:**
```css
a { color: #333333; }
```
`#333333` on a `#ffffff` background passes contrast (12.6:1) but is visually indistinguishable from body text if no underline or weight change is applied. Cannot confirm whether body `<a>` tags have additional visual differentiation without seeing the full HTML.

**Leftover template placeholder comment:**

"IMPUT" is a typo for "INPUT." This comment shipped in production, indicating the send checklist did not include a template-artifact review. No functional impact, but signals process gap.
