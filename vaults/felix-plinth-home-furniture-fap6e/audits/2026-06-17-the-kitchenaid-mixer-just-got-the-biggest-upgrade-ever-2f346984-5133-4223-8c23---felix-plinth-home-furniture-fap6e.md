# The KitchenAid mixer just got the biggest upgrade EVER

"Starts today!" "It's here!" "Psst... something new!" All week. ## What's working

- The creative pivot away from sale cadence is real and welcome — first non-warehouse email from C&B in my inbox all week, and that alone earns attention
- "KitchenAid" as a proper noun in the subject line is the right call; it's a brand I actually care about and it reads as specific product news, not a promo blast
- Hero image is product-forward — the mixer is the unambiguous subject of the frame, not buried in a lifestyle tableau
- Email renders cleanly: no broken images, no layout collapse, no overlapping text anywhere I can see
- The overall C&B color palette holds throughout — no off-brand module that looks like it was pasted in from a different template

## What's weak

- "EVER" in all caps is Wayfair flash-sale energy, not C&B — the brand's strength is restrained authority, and that word undercuts it immediately
- The body never answers the subject line's own question: what is the upgrade, specifically? If I opened because I wanted to know, I'm leaving without an answer unless I click
- No price anchor anywhere in the hero — this is a $500–$900 appliance decision for me; I need the number to decide whether this is a "now" or a "birthday" purchase
- The cross-sell grid below feels like a different email stapled on — the launch narrative and the "also here's some bowls" grid don't coexist gracefully
- Still lands in a week where C&B has been in my inbox what feels like every six hours — the fresh creative doesn't fully dissolve the fatigue

## Recommendations

- 1. **Put one concrete upgrade fact in the hero headline** — "Now with a 7-quart bowl" or "50% more powerful motor" beats "biggest upgrade EVER" for a buyer like me who needs a reason to click, not an adjective
- 2. **Show the price in the hero module** — or at minimum a "starting at $X" anchor; I'm not clicking into a PDP cold on a major appliance
- 3. **Treat the body as a KitchenAid family launch, not a general kitchen browse** — keep the cross-sell to mixer attachments and bowls that are genuinely part of this launch story, not random serveware
- 4. **Ditch the EVER cap** — reframe the launch with confidence, not exclamation-mark energy

### 3. Rendering & Accessibility

**Issue 3a — Unfilled template placeholder in `<head>` (HIGH)**
```html
<!--[IMPUT HERE CLIENT FONT IMPORT SCRIPT if needed]-->
<!---->
```
This is a raw, unresolved production comment from the template scaffolding, including a typo (`IMPUT` vs `INPUT`). It indicates the QA/render pass did not strip or validate template directives before send. Low rendering impact but confirms incomplete build pipeline discipline.

**Issue 3b — `maximum-scale=1` blocks accessibility zoom (MEDIUM)**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```
Prevents users from pinching to zoom on iOS/Android. Violates WCAG 2.1 SC 1.4.4 (Resize Text). Remove `maximum-scale=1`.

**Issue 3c — Conflicting `text-size-adjust` declarations (LOW)**
```css
html { -webkit-text-size-adjust: none; }   /* CLIENT styling block */
body { -webkit-text-size-adjust: 100%; }   /* General settings block */
*    { -webkit-text-size-adjust: none; }   /* universal selector, overrides body */
```
The universal `*` rule overrides the `body: 100%` rule. Net effect is `none` on all elements, which suppresses iOS automatic text resizing entirely. The intent of the `body: 100%` rule (preserve readability) is silently defeated. Consolidate to a single `html, body { -webkit-text-size-adjust: 100%; }` rule and remove the `*` declaration.

**Issue 3d — Conflicting desktop `img` max-width breakpoints (LOW)**
```css
@media only screen and (min-width: 768px) { img { max-width: 600px } }
@media only screen and (min-width: 640px) { img { max-width: 640px } }
```
Both blocks target desktop/wide viewports. On screens 640–767px wide, the 640px rule fires; on 768px+, the 768px rule fires — but because the 640px rule appears second in source order, it overrides the 768px rule for all screens ≥768px (cascade). The intended 600px cap at desktop widths never applies. Reverse source order or consolidate into one breakpoint.

**Issue 3e — `color-scheme` locked to light only**
```html
<meta name="color-scheme" content="light">
<meta name="supported-color-schemes" content="light">
```
Deliberately suppresses dark-mode rendering in Apple Mail and other clients that respect this meta. This is a known intentional pattern for brand control, but it means the email will not adapt in dark-mode inboxes and may trigger inverted-color accessibility modes on some clients. Flag if dark-mode support is a future requirement.

**Duplicate meta tags (INFORMATIONAL):**
`format-detection` appears four times (once combined, three individual). `charset` declared twice. Both are redundant but harmless; clean up for template hygiene.
