## Technical Audit

## 1. Technical Summary
The email is a table-based HTML 4.01 Transitional template, and the automated QA run passes 50% of checks. The one hard failure is a **0-character plain-text part**. The other findings are insecure `http://` asset and tracking URLs, missing alt attributes, and a viewport meta tag without a width. The HTML source was truncated, so anything in the footer or body past that point is unverified.

## 2. Link & Tracking Issues
- **13 tracking links were not probed.** They are on click-redirect domains (`click.comms.adidas.com`), so destination status, redirect chain and final landing URL are unverified.
- **Insecure tracking URL.** `http://click.comms.adidas.com/CI0/010201a0f41f7190-ab9230f3-e617-48d8-8b1b-b9489aa4e0d9-000000/8XVyofiBFxmXSqMpQ1MXsxXJZK5L1HiZQe5ujjDlWnE=452` is loaded as an `<img>` over plain HTTP. It appears to be the open-tracking pixel, though the truncated output doesn't confirm that. Clients that block mixed or non-HTTPS content will drop it, which undercounts opens. It also exposes the request to interception.
- **Insecure image host.** The image `arrow` (`b0c011a2-d468-414b-a8a2-8595b3ec7b34.jpg`) is served from `http://image.link.adidas.com/lib/fe6515707c62007e7715/m/3/…` and appears twice. The same asset family is otherwise available over HTTPS (`https://dv.adidas.com/o/…`), so the HTTP references look like a template inconsistency.

## 3. Rendering & Accessibility
- **Missing alt text, 2 images.**
  - `https://dv.adidas.com/o/6b0fce17-b48b-49b0-ba67-ae69bb2c6f54?cp_tp=…`
  - The tracking image above. A tracking pixel with no alt is low impact.
  - For the `dv.adidas.com` image, the QA output doesn't say whether it is content or decorative. If it is content, it needs descriptive alt text. If it is decorative, it needs `alt=""`.
- **Viewport meta has no width.** `<meta name="viewport" content="initial-scale=1.0">` lacks `width=device-width`. Most mobile clients handle this, but it is non-standard. The layout relies on `@media (max-width:639px)` rules.
- **Custom fonts never load.** The `@font-face` rules for `AdihausDIN` and `AdineuePRO` only use `src: local('Arial'), local('Helvetica'), …`. The brand fonts are not actually fetched, so every client falls back to system fonts. This is consistent, but the declarations do nothing.
- **Global `p` rule.** `p{margin:0 auto; text-align:center;}` applies to every paragraph in the email. Any `<p>` without an inline override will be centered.
- **Outdated doctype.** HTML 4.01 Transitional is acceptable for email but not modern.
