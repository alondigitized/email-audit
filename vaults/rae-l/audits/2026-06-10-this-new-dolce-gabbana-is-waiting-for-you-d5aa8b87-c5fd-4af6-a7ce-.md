### 3. Rendering & Accessibility

**External Google Fonts via `<link>` (blocked by most clients)**
```html
<link href="https://fonts.googleapis.com/css2?family=DM+Sans:...&display=swap" rel="stylesheet">
```
Gmail (web/Android), Outlook (all desktop), and Samsung Mail strip external `<link>` stylesheets. DM Sans will silently fall back to system fonts (`Helvetica, Arial, sans-serif` per the `.helvetica` fallback rule). Not breaking, but the intended typeface will not render for the majority of recipients.

**Global link color suppression — WCAG 1.4.1 violation**
```css
#MessageViewBody a {
  color: inherit !important;
  text-decoration: none !important;
  ...
}
```
This rule (targeting Gmail's webmail wrapper) removes all visual link differentiation. Any anchor without explicit inline `color` and `text-decoration` styles will be indistinguishable from body text — a confirmed accessibility failure under WCAG 1.4.1 (Use of Color).

**`translate="no"` on `<html>` root**
```html
<html lang="en-US" translate="no" ...>
```
Suppresses Gmail's and Chrome's auto-translate prompt for non-English-speaking recipients. Only acceptable if the email is exclusively targeted to English-language audiences; flag if international segments receive this send.

### 4. Personalization & Merge Tokens

**Suspicious trailing whitespace in `<title>`**

The trailing space after "Ulta Beauty" is consistent with an unresolved merge token (e.g., `Ulta Beauty [[FIRST_NAME]]` where the token rendered empty). This surfaces as the browser tab/preview title in some webmail clients. Verify against the ESP template source — if a token was intended, confirm fallback default is set.
