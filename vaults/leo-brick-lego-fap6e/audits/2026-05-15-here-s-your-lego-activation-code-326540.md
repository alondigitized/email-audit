# Here’s your LEGO® activation code: 326540
**Score:** 5/10 · **Type:** Email audit · **2026-05-15**
## Executive summary

- This is a transactional verification email, not a promotional one — and it's worth evaluating on that basis. Its sole job is to get a 6-digit code from the server into the user's hands as fast as possible, and it does that competently. The code sits dead-center in a bordered box, impossible to miss, with a plain-English expiry notice below it.
- The LEGO wizard minifigure is a small but smart touch: it adds warmth without eating up space or competing with the code. The light-blue branded background and clean white card layout are on-brand and render without any visible issues.
- The one notable missed opportunity is the highest-leverage move in transactional UX: putting the code in the subject line (which LEGO did — smart) but then not adding a one-tap "Copy code" button inside the email body. Everything else is execution polish, not a structural problem.

## What's working

- **Code in the subject line** — the recipient can see `326540` without opening the email at all. Best practice for OTP sends.
- **Code is unmissable** — large, centered, bordered box; the eye goes straight to it with no competing elements.
- **24-hour expiry is front and center** — no hunting through fine print.
- **"If you didn't sign up" message is clear and non-alarming** — good security hygiene surfaced at a natural reading position.
- **Brand character without clutter** — the wizard minifigure adds delight without adding noise.

## What's weak

- **No "Copy code" affordance** — there's no button or tap-to-copy mechanism; users must manually select and copy a 6-digit string.
- **No name personalization** — "Thanks for signing up" with no "Hi Alon," feels like a batch blast, not a triggered account email.
- **Copyright reads ©2022** — visibly dated footer erodes trust in an email asking users to take an account action.
- **"Contact customer service" is plain text** — appears unlinked in the render; a user who needs help has nowhere obvious to tap.

## Recommendations

- 1. **Add a tap-to-copy button** — a "Copy code" CTA button directly below the code box is the single highest-impact change. On mobile, selecting a 6-digit string is friction; a button eliminates it.
- 2. **Personalize the salutation** — "Hi Alon," before the body copy costs nothing and makes a triggered email feel triggered.
- 3. **Update the copyright year** — ©2022 in a 2026 email looks neglected. Automate this to the current year.
- 4. **Hyperlink "contact customer service"** — link it directly so tapping works.
- 5. **Strengthen the preheader** — if the preview is currently blank or falling back to body text, a dedicated preheader reinforces the urgency.
- **Subject Alt A:** `326540 is your LEGO® code — expires in 24h`
- **Subject Alt B:** `Activate your LEGO® account (code inside)`
- **Preheader Alt A:** `Copy this code to finish setting up your account. Valid for 24 hours.`
- **Preheader Alt B:** `One step away — here's your LEGO account activation code.`

## Technical Audit

## Technical Audit — LEGO® Account Activation Email

---

### 1. Technical Summary

This is a transactional OTP email generated via React Email (evidenced by `data-id="__react-email-column"` attributes) and relayed through `mail.identity.lego.com`. The QA run returned a 7% pass rate driven by asset-fetch failures, an HTML validity defect, and several CAN-SPAM gaps — though some QA findings are artifacts of the URL extraction method rather than live breakage.

---

### 2. Link & Tracking Issues

**Font CDN — 403 on both woff2 assets**

```
https://assets.lego.com/fonts/v6/typewell/LEGOTypewell-Regular.woff2  → 403
https://assets.lego.com/fonts/v6/typewell/LEGOTypewell-Bold.woff2     → 403
```

Both font files are blocked. Most likely CDN hotlink protection restricted to `lego.com` origin requests. Email clients that do fetch external fonts (Apple Mail, newer Outlook builds) will silently fall back to `Arial` per the `mso-font-alt` and `font-family` stack — functional but off-brand. The CSS already declares `mso-font-alt: 'Arial'` so this degrades gracefully, but the brand typeface will not render for any client that would have supported it.

**Background image — QA URL extraction artifact**

The checker flagged 422s on:
```
https://images.contentstack.io/v3/assets/.../bg.png);
https://images.contentstack.io/v3/assets/.../bg.png);background-repeat:no-repeat;...
```

The trailing CSS syntax (`)` and inline style text) was captured as part of the URL — these are malformed requests generated by the QA tool, not actual broken assets. The underlying image URL is valid. A solid `background-color: #BDDCFD` is declared as a fallback inline, so rendering degrades correctly if the image is unavailable.

**Footer link redirects**

The three footer links resolve to different paths than their `href` targets:

| `href` | Resolved path |
|---|---|
| `/en-US/legal/legal-notice/privacy-policy-full` | `/en-US/legal/notices-and-policies/privacy-policy` |
| `/en-US/legal/cookieinfo` | `/en-US/legal/cookies/cookie-policy` |
| `/en-US/service` | `/en-us/service` |

These are live 301/302 redirects, not broken links, but the `href` values are stale and add an unnecessary redirect hop. The legal URLs should be updated to their canonical paths.

**UTM parameters** — No UTM parameters on any links. For a transactional email this is low priority, but click attribution on the service/support link would be useful.

---

### 3. Rendering & Accessibility

**Invalid nested `<p>` elements**

Inside the `react-email-markdown` div, a `<p>` element directly wraps additional `<p>` elements:

```html
<p style="font-size:16px;...">
  <p>Thanks for signing up...</p>
  <p><span class="activation-code">326540</span></p>
  <p>Your code will work for 24 hours.</p>
  ...
</p>
```

Nested block-level elements inside `<p>` are invalid per HTML spec. Most email clients are lenient but some (notably older Outlook and Samsung Mail) will auto-close the outer `<p>` at the first inner `<p>`, potentially collapsing margins or breaking the layout block.

**`height="auto"` as HTML attribute**

```html
<img ... height="auto" width="180" />
```

`height="auto"` is not a valid HTML attribute value (it is valid only in CSS). Some older clients may treat this as `height="0"`. Should be `height=""` (omit) or set via `style="height:auto"`.

**Activation code accessibility**

The OTP `<span class="activation-code">326540</span>` has no ARIA label or `role` to identify it as a code to screen readers. Consider `aria-label="Activation code: 326540"` or wrapping in a `<code>` element.

**Stale copyright year**

```html
©2022 The LEGO Group.
```

Currently 2026. Minor but visible to recipients and affects perceived attention-to-detail.

### 5. Compliance (CAN-SPAM / RFC)

**Physical mailing address — missing**

CAN-SPAM §5(a)(5) requires a valid physical postal address in every commercial message. No physical address is present in the footer. While purely transactional emails (account activation) carry reduced CAN-SPAM obligations, the physical address requirement applies regardless of message type under the FTC's rules. This is a confirmed gap.

**No plain-text alternative**

The QA checker confirmed `0` characters in the plain-text part. A plain-text alternative is required for RFC 2822 compliance and expected by major ISPs for deliverability scoring. For an activation email, the plain-text body needs at minimum: the code, the expiry notice, and the customer service contact.

**Unsubscribe mechanism**

The QA flagged `[FAIL] No unsubscribe link found in body`. For a purely transactional one-time activation email, CAN-SPAM's opt-out requirement does not apply and this finding can be dismissed. However, the absence of `List-Unsubscribe` headers matters for inbox placement at Gmail and Yahoo (both now enforce sender requirements): if this sending domain sends any non-transactional mail without these headers, deliverability will be impacted.

**Authentication-Results header**

SPF/DKIM status not captured through the AgentMail relay. Cannot confirm pass/fail, but the sending domain `mail.identity.lego.com` should be verified to have DMARC alignment. No actionable finding without raw headers.

---

### 6. Email-to-Site Continuity

No deep-link to an account activation page — the email instructs the user to return to "the screen you just came from" without a direct URL. This is a deliberate UX pattern for OTP flows (avoids session mismatch) and is not a defect.

No UTM parameters are present on any footer links. For a transactional email, privacy-policy and cookie links do not require attribution, so this is acceptable.
