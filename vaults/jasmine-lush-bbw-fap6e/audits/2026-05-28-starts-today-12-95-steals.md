### 3. Rendering & Accessibility

**Two images with empty `src` — high severity**

QA flagged two `<img>` elements with both empty `src` and empty `alt`:
```
[WARN] Image missing alt text: : src:
[WARN] Image missing alt text: : src:
```
Broken `src` values cause visible broken-image icons in all clients. The empty `alt` compounds the accessibility failure. These are likely unfired template slots or Movable Ink blocks that failed to render.

**Three additional images missing `alt` text — medium severity**

- `418d0db7-5a65-43cb-b5c9-9c6c142e4fd2.png` — appears to be a content/product image; needs descriptive alt text for screen readers and image-blocked renders
- `4652086b90e6a651.png` (MI pixel) and the Everest pixel — functionally acceptable with `alt=""` for tracking pixels, but flagged by QA scanner

**Markup outside `<body>` — low severity**

The preheader `<table>` and open-pixel `<table>` are injected before the `<body>` tag in the serialized source. Most clients tolerate this, but it is malformed per spec and can produce unexpected behavior in stricter parsers.

**`<meta charset>` placement — low severity**

`<meta http-equiv="Content-Type" content="text/html; charset=utf-8">` is placed after the MSO conditional comment block rather than as the first element in `<head>`. Best practice is to declare charset before any non-ASCII content to prevent encoding misreads in legacy clients.

**Google Fonts import — informational**

`@import url('https://fonts.googleapis.com/css2?family=Source+Sans+Pro')` will be silently blocked by Gmail, Outlook, and most mobile clients. The fallback stack (Arial, Helvetica, sans-serif) is correctly defined on individual elements, so this is a degraded-but-functional render, not a bug.
