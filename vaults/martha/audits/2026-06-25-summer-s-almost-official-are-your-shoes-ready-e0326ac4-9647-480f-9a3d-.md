## Technical Audit — Skechers "Summer's Almost Official" Email

### 1. Technical Summary

The email's critical infrastructure issue is widespread mixed content: a majority of image assets are served over `http://` on a domain that should be HTTPS, making them likely to be blocked or proxied by modern email clients. The QA tool's summary line ("100% pass rate, 0 warnings") contradicts its own findings — 15 `[WARN]` entries were emitted and should not be dismissed.

---

### 2. Link & Tracking Issues

**Mixed-content tracking pixel (HTTP)**
`http://www.ink1000.com/p/up/7076d8b15a776085/o.gif?mi_u=8108404282&mi_ecmp=...`
— Plain HTTP. Gmail, Outlook.com, and Apple Mail proxy or strip non-HTTPS resources. This open-tracking pixel will silently fail in most clients.

**Static subscriber ID in Krux pixel**
`beacon.krxd.net/1x1_usermatch.gif?partner=...&partner_uid=122277199`
— `partner_uid` value appears hardcoded (a raw integer, not a merge token). If this is not dynamically populated per recipient, the user-match signal is corrupted for all sends.

**26 tracking links unverifiable**
All click-redirect links flow through `click.emails.skechers.com`. The QA tool skipped HTTP probing on all of them, so UTM parameter presence and destination alignment cannot be confirmed from this report alone. Requires manual spot-check or a separate link-crawler pass.

**`Return Path` pixel missing HTTPS**
`pixel.app.returnpath.net/pixel.gif?r=964ce1db...` — no scheme prefix in the extracted source. Should be confirmed as `https://`.

---

### 3. Rendering & Accessibility

**HTTP image sources — high severity**
13 images under `image.emails.skechers.com` are served over `http://`, including:
- The Skechers logo: `http://image.emails.skechers.com/.../dde00662-...png`
- All footer icons: App Store, Google Play, Curbside Pickup, AfterPay, Find A Store, Instagram, Facebook, YouTube

Gmail auto-proxies HTTP images through a Google cache; Outlook.com blocks them outright. Footer will likely render as broken images for Outlook.com recipients.

**Missing alt text on content image**
`https://image.emails.skechers.com/.../fad3dc53-...jpg` — a content image (not a tracking pixel) has no `alt` attribute. Screen readers will skip it; images-off rendering shows nothing.
Same issue on `49468f73-...png` (also HTTP).

**`-webkit-text-size-adjust: none` applied globally**
```css
* { -webkit-text-size-adjust: none; }
```
`none` prevents iOS Mail from scaling up small text, which fails WCAG 1.4.4. Should be `100%`.

**Malformed `<meta>` tags**
- `<meta content="text/html; charset=utf-8" />` — missing `http-equiv="Content-Type"`
- `<meta content="IE=Edge" />` — missing `http-equiv="X-UA-Compatible"`
Both attributes are required for the directives to take effect.

**Duplicate media query blocks**
Rules for the 375px and 640px breakpoints are defined twice — once in the first `<style>` block, once in a second `<style>` block inside `<body>`. The 375px block is a strict subset of the 640px block. No functional difference, but dead CSS weight and a maintenance risk.

**Preheader injection pattern**
```html
</head><body ...><style>div.preheader { display: none !important; }</style>
```
The hiding `<style>` is injected inside `<body>` after the closing `</head>`, rather than in `<head>`. Some clients with strict XHTML parsing may ignore it, causing the preheader text to render visibly.

### 4. Personalization & Merge Tokens

No unresolved merge token syntax (e.g., `%%FIELD%%` or `{{field}}`) visible in the truncated source — positive signal.

If these are not populated via ESP merge at send time, every recipient is tagged with the same identity — breaking retargeting and frequency-cap logic downstream.
