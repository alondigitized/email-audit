### 3. Rendering & Accessibility

**Issue — malformed `<meta>` tags (two instances):**

```html
<meta content="text/html; charset=utf-8" />        <!-- missing http-equiv -->
<meta content="IE=edge" />                          <!-- missing http-equiv -->
```

Both tags are missing the `http-equiv` attribute. The charset declaration should be:

```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=edge" />
```

Without `http-equiv`, the charset declaration is inert in some parsers, and the IE rendering directive is a no-op.

**Issue — `'Founders Grotesk'` referenced but never declared:**

```css
a { font-family: 'Founders Grotesk', Helvetica, sans-serif; }
```

Six `@font-face` blocks are present in `<style>` — all for Open Sans. `Founders Grotesk` has no corresponding declaration. All anchor text silently falls through to Helvetica. This is likely intentional as a system-font fallback, but it means the designed weight/tracking on links is never applied in any client.

**Issue — Google Fonts loaded from external CDN:**

All six Open Sans variants fetch from `https://fonts.gstatic.com/s/opensans/v17/...`. Gmail strips `<head>` CSS blocks entirely; Outlook (all versions) ignores web fonts. The `v17` slug also references a 2019 build — current Google Fonts serves v29+, though gstatic CDN continues to serve versioned paths indefinitely.

**Issue — `img { white-space: pre; }`:**

This property is non-standard on `<img>` elements and has undefined behavior. It is harmless in most clients but should be removed to avoid unexpected reflow in Outlook or legacy WebKit renderers.

**Note — `body {}` smoothing rules:**

```css
body { -webkit-font-smoothing: antialiased; -moz-osx-font-smoothing: grayscale; text-rendering: optimizeLegibility; }
```

These are stripped by Gmail, Outlook, and most webmail clients. No rendering impact in practice.
