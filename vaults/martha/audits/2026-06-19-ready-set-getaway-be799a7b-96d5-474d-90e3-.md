- **"Summer getaway" is someone else's summer** — I am a mom of a 5- and 9-year-old in June. A travel kit checklist is aspirational to the point of irrelevance for my day-to-day.

## Technical Audit — Sally Beauty "Ready, Set, Getaway" Email

### 1. Technical Summary

The email uses a standard XHTML 1.0 Transitional table-based layout with responsive media queries. Two malformed meta tags and a non-standard `img` CSS property are the most actionable rendering risks; the full source is truncated so compliance items (unsubscribe footer, tracking pixel) cannot be fully verified.

---

### 2. Link & Tracking Issues

**Cannot fully audit** — no anchor tags or tracking pixels appear in the provided truncated source. The following is noted from the `<head>`:

- **Google Fonts URLs are pinned to `v17`** (`fonts.gstatic.com/s/opensans/v17/...`). Google does not guarantee indefinitely serving versioned static paths. These URLs are from approximately 2019 and current Open Sans is at v40+. If Google deprecates the `v17` path, font fallback silently kicks in — no visible error, but brand typography breaks. Recommend switching to the standard `fonts.googleapis.com/css2?family=Open+Sans` API URL, which always serves the current version.

---

### 3. Rendering & Accessibility

**`img { white-space: pre; }` (global CSS rule)**
This is non-standard on `<img>` elements. `white-space` applies to inline text content, not replaced elements. Its presence is likely a copy-paste artifact. In some Outlook and older WebKit-based clients it can force images into unexpected layout contexts. Remove it.

**Malformed `<meta>` tags — missing `http-equiv` attribute:**
```html
<!-- As written — invalid -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=edge" />

<!-- Correct form -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=edge" />
```
Without `http-equiv`, both tags are no-ops. The charset declaration in particular is meaningless, leaving encoding resolution entirely to the sending server's `Content-Type` header.

**`Founders Grotesk` referenced but never loaded:**
```css
a { font-family: 'Founders Grotesk', Helvetica, sans-serif; }
```
There is no `@font-face` declaration for `Founders Grotesk` in the source. Every link in the email falls back to Helvetica. This is a rendering inconsistency if desktop renders were approved with the custom font installed locally on a designer's machine.
