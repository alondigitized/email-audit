### 1. Technical Summary

The email uses a standard SFMC/table-based template with functional responsive CSS and no broken links detected. The primary technical risks are a systemic HTTP (non-HTTPS) image delivery pattern across all hosted assets and two third-party tracking pixels that present minor privacy-signal concerns.

---

### 2. Link & Tracking Issues

**Third-party data sync pixels embedded in hidden `<div>`:**
- `beacon.krxd.net/1x1_usermatch.gif` — fires twice, syncing SFMC subscriber ID (`122277199`) and SHA-256 hashed email to Salesforce/Krux DMP
- `beacon.krxd.net/1x1_ad_impression.gif` — logs ad impression with `campaignid=PRO_US_NA_U_SITEBUNDLE_LOYL_EN_06252026`
- `pixel.app.returnpath.net/pixel.gif` — Return Path/Validity inbox monitoring pixel

These are loaded inside a `display:none` `<div>` nested in a zero-font-size `<td>` — a double-hidden pattern. The pixels will still fire on HTML load, but the nesting is non-standard and could be flagged by aggressive email clients stripping invisible content.

**26 click-redirect links** all route through `click.emails.skechers.com` (SFMC click tracking). Not auditable for destination without resolving, but the domain is consistent and expected.

---

### 3. Rendering & Accessibility

**HTTP image sources — affects all hosted assets (14 images flagged):**

Every image from `image.emails.skechers.com` is served over HTTP, not HTTPS:
```
http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/1/dde00662-...png   (logo)
http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/11/49468f73-...png  (no alt)
http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/11/0ec56c9f-...png  (App Store)
... (11 additional images, same pattern)
```

Gmail, Yahoo, and Outlook.com proxy all remote images through HTTPS rewrites — HTTP sources are either silently upgraded or blocked depending on the client. Apple Mail on iOS 15+ and most modern clients will block mixed-content images. The Skechers logo and product imagery are at risk of rendering as broken images in security-strict clients.

**Third-party open-tracker also HTTP:**
```
http://www.ink1000.com/p/up/7076d8b15a776085/o.gif  (missing alt="")
```
This pixel has no `alt` attribute and is HTTP. If blocked, it generates a broken image icon rather than collapsing cleanly.

**Missing `alt` text on two images:**
- `o.gif` (ink1000 tracker) — no `alt` attribute at all
- `49468f73-4651-4af3-bea2-61d1ae5db486.png` — no `alt` attribute; content unknown from truncated source, likely a product or promo image

**`<meta>` tags missing `http-equiv` attributes:**
```html
<meta content="text/html; charset=utf-8" />   <!-- missing http-equiv="Content-Type" -->
<meta content="IE=Edge" />                     <!-- missing http-equiv="X-UA-Compatible" -->
```
Both `http-equiv` attributes are absent, making these tags non-functional. The charset declaration in particular should be `<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />` for full XHTML compliance per the declared DOCTYPE.

**Duplicate responsive breakpoints:** `.hideme`/`.hidden`/`.mobile-hidden` rules are declared identically in three separate `@media` blocks (`max-width: 375px`, `max-width: 640px`, `max-width: 480px`). No functional breakage, but dead CSS weight.
