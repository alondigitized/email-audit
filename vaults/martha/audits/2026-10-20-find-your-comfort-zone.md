## Technical Audit

## 1. Technical Summary
The email has one confirmed personalization failure (empty greeting, `Hi ,`) and several markup defects in the tracking-pixel layer: a scheme-less pixel URL, `http://` image sources, and missing `alt` attributes. Link, unsubscribe and header checks could not be completed because the HTML source is truncated and the `Authentication-Results` header is absent from the relay.

## 2. Link & Tracking Issues
- **Broken pixel URL.** `<img src="pixel.app.returnpath.net/pixel.gif?r=964ce1db…">` has no scheme. Clients resolve it as a relative path against the message or host, so the request fails and the Return Path/Validity seed-tracking pixel never fires. It also has no `alt`.
- **Insecure open pixel.** `http://www.ink1000.com/p/up/7076d8b15a776085/o.gif?mi_u=8108404282&mi_ecmp=MKG_US_NA_U_COMF_PROD_EN_10202026` is plain HTTP. Gmail's image proxy or Apple Mail Privacy Protection may block or rewrite it, and it can trigger mixed-content warnings.
- **Unverified links.** 35 tracking links were skipped by the HTTP probe because they are click-redirect domains (for example `click.emails.skechers.com`). Their destinations, status codes and redirect chains are unverified, not confirmed healthy.
- **Third-party data pixels.** Three `beacon.krxd.net/1x1_usermatch.gif` and `1x1_ad_impression.gif` pixels sit in the hidden block. They are HTTPS, but they add third-party calls and have no `alt`. See Compliance for the data they carry.

## 3. Rendering & Accessibility
- **Missing `alt` (QA-confirmed):** `o.gif` (ink1000.com) and `dde00662-169f-447d-b0e2-fc65f6c2290c.png`. The PNG's name suggests it may be a content image rather than a spacer. If so, it has no accessible name.
- **Non-HTTPS content image (QA-confirmed):** `http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/1/dde00662-….png` may be blocked or shown as a broken image.
- **Zoom disabled:** `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">`. `maximum-scale=1` blocks pinch-zoom, which is a WCAG 1.4.4 issue.
- **Malformed meta tags:**
  - `<meta content="text/html; charset=utf-8" />` has no `http-equiv`, so it declares nothing.
  - `<meta content="IE=Edge" />` also has no `http-equiv`, so it declares nothing.
- **No `lang` attribute** on `<html xmlns="http://www.w3.org/1999/xhtml">`, so screen readers can't pick the right language profile.
- **Layout tables:** the visible tables (`<table class="widthFull" width="640" …>`) have no `role="presentation"`.
- **Text scaling:** `* { -webkit-text-size-adjust: none; }` stops iOS from scaling text for users who need larger text.
- **Not assessable:** the source is truncated, so body content, link text and button markup could not be checked.

## 4. Personalization & Merge Tokens
- **[FAIL] Empty greeting slot.** The greeting renders as `Hi ,` because the first-name field was empty. The send has no fallback value or conditional, so subscribers without a first name get a broken salutation. The failing greeting is outside the truncated excerpt, so I can't quote the token syntax.
- No other unresolved tokens (`%%…%%`, `{{…}}`) are visible in the excerpt.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- **Authentication:** `Authentication-Results` was not found. This is attributed to the AgentMail relay, so SPF, DKIM and DMARC status for `emails.skechers.com` is unknown, not failed. Check it in a direct-delivery test.
- **Unsubscribe and postal address:** the footer and the `List-Unsubscribe` / `List-Unsubscribe-Post` headers are not in the provided data, so I can't confirm or deny one-click unsubscribe or the physical address. No finding either way.
- **Hashed email in third-party pixels.** The krxd.net URLs carry `partner_uid=adf27fee…189a` (a 64-hex value, apparently a SHA-256 hash, under `partner=…_sha25…`) and `partner_uid=122277199` (a subscriber ID). Hashed email is still personal data. This is a privacy-disclosure item to confirm against the sender's privacy policy and consent handling, not a CAN-SPAM violation.
- **Sender address:** `no-reply@emails.skechers.com`. This is not a CAN-SPAM violation if the unsubscribe path works, but it removes a reply channel.

## 6. Email-to-Site Continuity (UTM params, landing page alignment)
- The campaign identifier `MKG_US_NA_U_COMF_PROD_EN_10202026` appears in the ink1000 and krxd pixels, so campaign tagging exists at the pixel level.
- UTM parameters on the CTA links and landing-page alignment could not be verified. The 35 links are behind click-tracking redirects that the probe skipped, and the HTML is truncated. No finding.

## 7. Recommendations
1. **Fix the greeting.** Add a fallback to the first-name token (for example, `Hi there,` or drop the name when empty). This is the only confirmed customer-visible defect.
2. **Fix the Return Path pixel.** Change it to `https://pixel.app.returnpath.net/pixel.gif?r=…`.
3. **Move to HTTPS.** Serve `ink1000.com/…/o.gif` and `image.emails.skechers.com/…/dde00662-….png` over `https://`. Confirm the hosts support TLS.
4. **Add `alt` text.** Use `alt=""` on tracking pixels and descriptive `alt` on the PNG if it carries content.
5. **Repair the head.**
   - Use `<meta http-equiv="Content-Type" content="text/html; charset=utf-8">`.
   - Use `<meta http-equiv="X-UA-Compatible" content="IE=edge">`.
   - Remove `maximum-scale=1` from the viewport tag.
   - Add `lang="en"` to `<html>`.
   - Add `role="presentation"` to layout tables.
6. **Re-run with full data.** Capture the full HTML, raw headers (`Authentication-Results`, `List-Unsubscribe`, `List-Unsubscribe-Post`, DKIM-Signature) and resolved redirect targets, so UTM, unsubscribe and authentication can be audited.
7. **Review the krxd pixels.** Confirm with privacy/legal that the hashed-email data sharing is covered by the sender's disclosures.
