# In the app: 25% OFF & best sellers
**Score:** 7/10 · **Type:** Email audit · **2026-06-02**
## Executive summary

- DSW again. Yesterday it was the app-exclusive 25% offer, and now here's a follow-up that's essentially the same pitch — in-app deal, summer styles — dressed up with a Father's Day hook in the preview. The "Here's what Dad really wants" line actually made me pause for a second because I am a dad, and Father's Day is coming. But then I open it and the first thing I see is sandals, high heels, and strappy women's styles stacked top to bottom. Where am I in this email? I see a "SHOP SNEAKERS" and a "SHOP ACTIVE SNEAKERS" row buried in the middle, but that's it. The 25% off app-exclusive offer is front and center and that part is clean. The size-filter section at the bottom is a nice touch. But this reads like a women's email that got the wrong list segment.
- I'd click the sneakers section out of habit, maybe check the active sneakers. But I'm not forwarding this to anyone. Mark as read, check DSW's site directly if I want a pair of walkers.

## What's working

- **25% off is hard and clear** — the hero banner leads with "IN-APP EXCLUSIVE 25% OFF*" and I see it immediately without scrolling.
- **"SHOP ACTIVE SNEAKERS"** row is something I'd tap — that's the category that matters to me, even if it's buried halfway down.
- **"SHOP BY SIZE"** grid at the bottom is genuinely useful. At my age I know what size I wear; let me start there.
- **Preview text delivers a different angle** — "Here's what Dad really wants" isn't just echoing the subject, and Father's Day timing is relevant to me personally.
- **Clean layout, no broken images** — the grid renders fine and the visual hierarchy doesn't fight itself.

## What's weak

- **Women's shoes dominate the visible real estate** — sandals, strappy heels, kitten mules — none of that is my aisle.
- **"In-app exclusive" is a wall, not a welcome** — I have to use the DSW app to get the deal. That's friction. I shop on a browser.
- **The asterisk on 25% OFF*** is doing a lot of work — I can see it but I can't read the fine print. That's a signal to be cautious.
- **No comfort language anywhere** — cushion, arch, wide width, walking shoe — not a word. If DSW knows I'm a comfort shopper, they're not showing it.
- **Same campaign beat two days running** — this is the second app-exclusive email in 24 hours. DSW's been hammering me: BOGO sandals all through May, then the Pride send, then yesterday's app email, now this one. The Father's Day angle is fresh but the offer structure is a copy-paste.

## Recommendations

- 1. **Lead the men's comfort footwear block** — if the list is segmented male, the hero product grid should be men's walkers, sneakers, or slip-ons. Move the women's sections to the second half.
- 2. **Make the Father's Day angle pay off** — the preview says "what Dad really wants." The email should open on a men's gifting block, not women's sandals. One curated "Dad's Picks" row with 3-4 comfort shoes would match the promise.
- 3. **Drop the app wall or add a browser fallback** — "App exclusive" alienates anyone not on the app. A note like "or use code DAD25 online" keeps the deal accessible.
- 4. **Surface comfort-specific copy** — one line in the hero or section header mentioning cushioning, arch support, or wide widths would signal DSW knows who I am.
- 5. **Add a deadline to the 25% off** — "ends Sunday" or "Father's Day weekend only" turns a standing offer into a reason to act today.

- **Subject Alt B:** `Comfort shoes for Dad — 25% off this weekend`
- **Preheader Alt A:** `Men's walkers, sneakers & slip-ons he'll actually wear`

### 3. Rendering & Accessibility

**`http-equiv` missing on two meta tags** — both tags will be ignored by strict parsers:
```html
<!-- As written (broken) -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=Edge" />

<!-- Correct -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```

**`@font-face` uses capitalized `Src:` property** (all 10 declarations) — invalid CSS per spec. Gecko-based clients will reject these rules; font fallback will fire silently:
```css
/* All 10 @font-face blocks contain: */
Src: url("https://braze-images.com/...") format('woff');
/* Should be lowercase: */
src: url("...") format('woff');
```

**`maximum-scale=1` in viewport meta** — blocks pinch-to-zoom; violates WCAG 1.4.4 (Resize Text, AA). Common in email templates but worth flagging if accessibility compliance is required:
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```

**`text-size-adjust: none` in global reset** — the `*` rule sets `-ms-text-size-adjust: none` while simultaneously setting `-webkit-text-size-adjust: 100%`. These are inconsistent; `none` disables OS-level text scaling on Windows/IE, whereas `100%` allows it on WebKit. Standardize to `100%` across all prefixes.

**All `@font-face` variants declare `font-weight: normal`** — Bold, Demi, and Medium cuts each declare `font-weight: normal`. This means the faces can only be invoked by explicit `font-family` name (e.g., `font-family: 'Futura_PT_Bold'`), not by CSS `font-weight: bold` on a parent element. This is a common Braze pattern but creates fragility if any template block uses weight-based inheritance.

**`supported-color-schemes` as a CSS property in `:root`** — this is not a valid CSS property; it belongs only as a `<meta>` tag (already correctly present in `<head>`). The `:root` declaration is a no-op and adds dead code:
```css
:root {
  supported-color-schemes: light dark; /* invalid CSS, remove */
}
```
