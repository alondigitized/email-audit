## Technical Audit

## 1. Technical Summary
Standard SFMC-served responsive marketing email with correct viewport/media-query scaffolding, but multiple tracking/branding assets are served over plain HTTP and two images lack alt text.

## 2. Link & Tracking Issues
- Open-tracking pixel present: `click.emails.skechers.com/open.aspx?MZRXXZVLMDVUJLO6YUREZNRBPI.100228&d=100228&bmt=0`.
- Multiple third-party tracking pixels fire: Krux/Salesforce DMP beacons (`beacon.krxd.net/1x1_usermatch.gif`, `1x1_ad_impression.gif`), Return Path pixel (`pixel.app.returnpath.net/pixel.gif` — protocol-relative, no scheme specified), and an Ink1000 engagement pixel (`www.ink1000.com/p/up/7076d8b15a776085/o.gif`).
- QA flagged 33 tracking/click-redirect links skipped from HTTP probing (expected behavior for redirect-domain links; not itself an error, but means link destinations were not validated end-to-end).
- The Ink1000 pixel (`o.gif`) is loaded over **http://**, not https — flagged by QA.

## 3. Rendering & Accessibility
- Two images missing `alt` text (QA-confirmed):
  - `o.gif` (Ink1000 tracking pixel) — acceptable for a 1x1 tracking pixel, but should still carry `alt=""` explicitly (it's absent, not empty).
  - `49468f73-4651-4af3-bea2-61d1ae5db486.png` — a content image with no alt attribute at all; this is a real accessibility gap for screen-reader users.
- Mobile/desktop toggling relies on `display:none/block` via `.mobile-content`/`.desktop-content` classes gated on `min-width:768px` — some mail clients (notably Outlook desktop) strip `<style>` media queries, which can cause both blocks to render simultaneously or the mobile block to be hidden entirely. Worth a client-matrix check (Outlook, Gmail app).
- Responsive breakpoints are duplicated at both 375px and 640px with identical rule sets — redundant but not a functional bug.

## 4. Personalization & Merge Tokens
No merge/personalization tokens (e.g. `%%FirstName%%`, AMPscript) are visible in the truncated source. No issues found based on available markup.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- Sender: `no-reply@emails.skechers.com` — a `no-reply` reply-to address is a CAN-SPAM soft-flag (not itself a violation, but reduces user recourse); not evaluable further without header data.

- SPF/DKIM/DMARC authentication headers were not included in the provided data — cannot assess.

## 7. Recommendations
1. Serve all image assets over HTTPS — 8 assets (logo, product image, app-store badges, payment/social/footer icons) currently load via `http://image.emails.skechers.com/...` and `http://www.ink1000.com/...`, which many mail clients will block or flag as mixed content.

3. Verify unsubscribe link and physical address render correctly in the full (untruncated) footer — not visible in the provided source excerpt.
