## 1. Executive Summary

I'm a 62-year-old guy who just wants to find a good pair of slip-ins without fighting the website. Today's visit had some bright spots — the Men's nav menu is clean, the Slip-ins category page is exactly what I need — but the same old problems are still there. Homepage is pushing Mother's Day stuff at me, I never actually saw a login form, search dumped Women's shoes at me first, and worst of all: **the cart page was completely blank**. Can't buy what I can't see in my cart. This site is still leaving money on the table.

## Technical Audit

## Technical Summary

The skechers.com mobile journey shows structurally sound server response times but is undermined by: 30 axe violations (4 critical) concentrated on the product page, systematic 429 errors from Kasada's own bot-detection fingerprinting endpoint, a broken Stylitics widget due to CORS misconfiguration, and an extremely heavy third-party script payload with duplicate script loads. LCP and CLS were not captured for any step — a significant measurement gap.

---

## Accessibility

**30 violations total; 4 critical, 6 serious.**

**Critical (must fix):**
- `image-alt` — `<img>` elements missing `alt` on View Product. Fails WCAG 1.1.1.
- `button-name` — buttons with no discernible text on View Product. Fails WCAG 4.1.2.
- `aria-required-children` — ARIA role missing required child roles on View Product. Invalid ARIA tree.
- `aria-valid-attr-value` — invalid ARIA attribute values on View Product. Likely `aria-*=""` or malformed IDs.

**Serious:**
- `link-name` (Homepage) — anchor elements with no accessible text; likely icon-only links with no `aria-label`.
- `link-in-text-block` (Men's Shoes) — links distinguished only by color; fails WCAG 1.4.1.
- `aria-dialog-name` (View Product) — modal/dialog missing `aria-label` or `aria-labelledby`.
- `aria-input-field-name` (View Product) — form inputs with ARIA roles but no accessible name.
- `color-contrast` (View Product) — foreground/background fails WCAG AA ratio.

**Moderate (structural, affects AT navigation):**
- Duplicate `main` landmark (Homepage) — two `<main>` elements or nested landmark.
- `landmark-complementary-is-top-level` on Homepage and Men's Shoes — `<aside>` nested inside another landmark.
- `heading-order` (Homepage) — heading levels skip (e.g., h1 → h3).

The density of critical violations on View Product suggests the product detail page (likely a modal or SPA-injected overlay) was built without accessibility review.

## SEO

**Third-party script volume is the primary SEO risk.** The page fires 20+ async third-party scripts before any meaningful content renders. While `async` prevents parser blocking, Googlebot's JavaScript rendering budget is finite — late-injected content (via Monetate, Bloomreach, etc.) may not be indexed.

**Observed issues:**
- Monetate loads two concurrent versions: `se.monetate.net/js/3/...` and `//se.monetate.net/js/2/...`. This is redundant and adds payload.
- WebFontLoader (v1.6.28 from cdnjs) applies `wf-loading` class to `<html>` during font resolution. If fonts are slow, text remains invisible — potential FOIT impacting perceived content completeness for crawlers.
- The HTML snippet shows no `<link rel="canonical">` or structured data in the visible fragment. Cannot confirm presence without full source.
- `--vh` is computed server-side or early JS — not an SEO issue, but confirms layout depends on JS.

## Mobile Optimization

- `--vh: 6.640000000000001px` is set inline on `<html>` — this is a JavaScript-computed viewport height unit to work around the iOS Safari address-bar collapse behavior. The fractional pixel value (`6.64000...1`) is a floating-point artifact and is functionally fine, but suggests this is computed naively rather than via `env(safe-area-inset-*)`.
- CLS is unmeasured — mobile is more susceptible to layout shift from below-the-fold images loading, dynamic banners, and consent overlays. Monetate in particular is a known CLS source.
- No `loading="lazy"` or `fetchpriority="high"` attributes are visible in the HTML samples — cannot confirm LCP image is prioritized.
- The page uses WebFontLoader rather than `<link rel="preload">` for fonts — this defers font loading and risks FOIT on slow mobile connections.

## Console & Network Errors

**429 — Kasada fingerprint endpoint (5 hits):**
```
/149e9513.../fp?x-kpsdk-v=j-1.2.308
```
Kasada is Skechers' bot-mitigation layer. The `/fp` endpoint is Kasada's own JavaScript fingerprinting collector. Getting 429s on it means Kasada is rate-limiting its own script — almost certainly because the automated test session triggered bot-detection heuristics, causing the Kasada client to retry beyond its quota. **This is not a real-user bug** in normal conditions, but it confirms the test runner was flagged as a bot and Kasada's retry logic is aggressive.

**429 — `/cart/` (1 hit):**
```
429 https://www.skechers.com/cart/
```
This is a genuine concern. A 429 on the cart page during what appears to be a legitimate user session (not just the fingerprinting endpoint) suggests either: (a) the same bot-detection flag blocked the page load entirely, or (b) there is a separate rate limit on cart. If real users hit this, it is a hard conversion blocker.

**CORS — Stylitics widget (2 blocked + 2 failed):**
```
https://web-assets.stylitics.com/style.css?base=hotspots&theme=skechers&version=50a631f787
```
Stylitics' CDN is not returning `Access-Control-Allow-Origin: https://www.skechers.com`. The stylesheet is attempted as both a `<link>` and an `XMLHttpRequest` (the latter being the fallback), both blocked. The Stylitics "Shop the Look" / hotspot widget will be **completely non-functional** — no styles load. This is a vendor-side misconfiguration (Stylitics must add the CORS header), but Skechers should open a ticket with Stylitics immediately.
