## Technical Audit

## 1. Technical Summary
The email is a Cordial-sent campaign (`e.emails.hoka.com`) with consistent UTM tagging. The QA run flagged all 12 probed tracked links as failing and found no plain-text part. The link failures are probably bot-blocking by the tracker rather than dead links, and the other findings are markup and accessibility gaps.

## 2. Link & Tracking Issues
- **All 12 probed links failed.** Eleven returned 406 (logo, hero and product images, return-start link) and the Unsubscribe link returned 403. Every failing URL is a Cordial click-tracker redirect (`https://e.emails.hoka.com/c2/1664:6aceb994bfd8bfd5670294b8:ot:…:1/<hash>?jwtH=…&jwtP=…&jwtS=…`).
- **This looks like a probe artifact, not proof of broken links.** A uniform 406/403 across unrelated destinations points to the tracker rejecting a non-browser User-Agent. The 15 skipped links were not checked at all.
- **Destinations are valid.** The base64 `linkUrl` claim in each `jwtP` payload decodes to well-formed `www.hoka.com` URLs. Examples are `https://www.hoka.com/en/us/wide/`, `.../womens-everyday-running-shoes/bondi-9/1162012.html?dwvar_1162012_color=ATRM&dwvar_1162012_width=Wide`, and `https://www.hoka.com/en/us/return-start/`. Re-test from a browser-like client before treating any of these as defects.
- **Every link is wrapped in a signed JWT redirect.** Destination URLs can't be seen without decoding. Some clients and security scanners may pre-fetch and flag these, which is a deliverability consideration only.
- **Tracking pixels are present.** There is one at `e.emails.hoka.com/o/p/…` and one at `mg.emails.hoka.com/o/…` (a second sending domain). Both lack `alt`, which is normal for pixels.

## 3. Rendering & Accessibility
- **Alt text:** 11 content images have no `alt`. These are `US_20261029_WidStyles_b/c/d/e.jpg`, the four product images (Bondi 9, Arahi 9, Challenger 8, Speedgoat 7), both Bondi SR images, `US_Q3_ShoeFinder_Yellow.jpg` and `LogoFooterPrimary.png`. The product images are wrapped in links, so link text falls back to the filename, for example `[image: US_Bondi9_TopLeft_1186830-ATRM.jpg]`. Screen readers and image-blocking clients get no usable label or destination.
- **Empty `<title>`:** `<title></title>`.
- **Ineffective charset declaration:** `<meta content="text/html; charset=utf-8" />` has no `http-equiv="Content-Type"` or `charset=` attribute. Rely on the HTTP header instead.
- **Duplicate, conflicting viewport tags:** the first is `width=device-width, initial-scale=1, maximum-scale=1`. The second is `…maximum-scale=1, user-scalable=yes`. `maximum-scale=1` restricts pinch-zoom on some clients, which is an accessibility issue.
- **Invalid CSS:** `.nav_padding {padding-top:px !important;padding-bottom:px !important;}` and `.nav_border {border-top:px solid ;}` have empty values. These are template leftovers that are ignored, but they indicate unpopulated variables.
- **Reset side effect:** `* {outline:none;}` removes focus indicators, a minor keyboard-accessibility issue.
- **Dark-mode colors:** link color `#000001` and footer `#fffffe` are the usual dark-mode workaround. That's fine, not a defect.

## 4. Personalization & Merge Tokens
No issues found. The truncated source shows no unrendered tokens (`{{…}}`, `%%…%%`). The `hmail=` parameter (a 64-hex hash) and `cordial_id=` are populated in every decoded URL. The source was truncated, so the footer and later body were not inspected.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- **Plain-text part missing:** the QA reports "Text version is 0 chars". If this reflects the real MIME structure and not an AgentMail extraction limit, it's a deliverability and accessibility gap.
- **Authentication unverified:** `Authentication-Results` was not found. The check says SPF/DKIM/DMARC status is unknown because of the AgentMail relay, so no pass or fail can be claimed.
- **Unsubscribe link is present:** it is labeled "Unsubscribe" and decodes to `https://options.hoka.com/unsubscribe?cid=69e560485cc95da09e001cd9&utm_…`. The 403 is the same tracker-probe behavior as above, so it is unconfirmed rather than failed.
- **Not assessable from the provided data:** `List-Unsubscribe` / `List-Unsubscribe-Post` headers and the physical postal address (the footer was truncated).

## 6. Email-to-Site Continuity (UTM params, landing page alignment)
- **UTM tagging is consistent across all decoded links:** `utm_source=US_Broadcast&utm_medium=email&utm_campaign=H_US_BR_20261027_Wides_STO_A120Day_365WidesTag_WidesPLPBrowsers_Post0928OptIns_AIRFMMedium`.
- **Landing pages match the "Need it in Wide?" subject.** Product links carry `dwvar_<pid>_width=Wide` and a color variant, so they should land on pre-selected wide-width PDPs. The hero and style tiles go to `/en/us/wide/`.
- **UTM tagging is inconsistent in one place.** The "HOKA" logo link goes to the bare `https://www.hoka.com/?utm_…` homepage, which is fine. `utm_content` is absent everywhere, so individual tiles can't be told apart in analytics.
- **Naming mismatch:** the campaign name says `20261027`, but the image assets are named `US_20261029_…`. This is likely an asset reuse or naming slip with no functional impact.

## 7. Recommendations
1. Re-probe the tracked links with a browser-like User-Agent, or decode and test the `linkUrl` targets directly. Don't treat the 406/403 results as real breakage until then.
2. Add descriptive `alt` text to all 11 content images, especially the linked product tiles. Keep the pixel images' `alt=""`.
3. Fill in `<title>`, add `<meta http-equiv="Content-Type" content="text/html; charset=utf-8">`, and drop the duplicate viewport tag and `maximum-scale=1`.
4. Confirm a `text/plain` MIME part exists in the original message. If it doesn't, add one.
5. Capture the raw headers to verify SPF/DKIM/DMARC alignment and `List-Unsubscribe` / `List-Unsubscribe-Post` for one-click support.
6. Add `utm_content` per tile and remove the empty-value CSS rules (`padding-top:px`, `border-top:px solid`).
