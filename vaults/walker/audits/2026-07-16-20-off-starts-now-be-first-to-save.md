---

### 3. Rendering & Accessibility

**[CONFIRMED BUG] Two meta tags are missing their `http-equiv` attribute:**

```html
<!-- As written — attribute is ignored by parsers -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=Edge" />

<!-- Should be -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```

Without `http-equiv="Content-Type"`, the charset declaration is inert in some clients. Without `http-equiv="X-UA-Compatible"`, the IE/Outlook Edge mode hint does nothing.

**[CONFIRMED BUG] All 10 `@font-face` blocks use capitalized `Src:` instead of `src:`:**

```css
/* All 10 declarations have this: */
Src: url("https://braze-images.com/appboy/...") format('woff');
```

CSS property names are technically case-insensitive per spec, but several email client CSS preprocessors (notably Outlook's Word renderer and some SFMC/Braze inlining tools) will reject or drop properties with non-lowercase names. Futura and HelveticaNow fallbacks to system fonts will silently kick in wherever this fails.

**[MINOR] `text-size-adjust: none`** is set globally via `*` selector in the reset. The intent is presumably `100%` (suppress auto-scaling), not `none` (disable the property entirely). `none` can cause text to render at unexpected sizes in some WebKit clients.

**`<title>DSW</title>`** — not a bug, but some screen reader configurations announce the document title; a subject-matching title (or at minimum `DSW Email`) is more accessible.
