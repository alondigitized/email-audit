### 3. Rendering & Accessibility

**Issue 3a — Malformed `<meta>` tags (missing `http-equiv`)**

```html
<!-- Found in source -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=Edge" />
```

Both tags are missing the required `http-equiv` attribute. Correct forms:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```
Without `http-equiv="Content-Type"`, some legacy clients may default to ASCII and mangle non-ASCII characters.

**Issue 3b — `maximum-scale=1` locks user zoom**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```

`maximum-scale=1` prevents pinch-to-zoom. This fails **WCAG 1.4.4 (Resize Text, Level AA)** and is flagged by accessibility auditors. Remove `maximum-scale=1` or set `maximum-scale=5`.

**Issue 3c — HelveticaNow fonts declared as TTF only, no WOFF**

```css
/* HelveticaNow — TTF only */
Src: url("https://braze-images.com/.../original.ttf?1755182939") format('truetype');

/* Futura PT — WOFF (correct) */
Src: url("https://braze-images.com/.../original.woff") format('woff');
```

TTF is supported in Apple Mail and some webmail clients but **not in Outlook on Windows** (which ignores web fonts entirely but falls back safely) and has inconsistent support in Gmail. The inconsistency between the two font families (Futura PT gets WOFF; HelveticaNow gets TTF only) suggests an oversight. Add WOFF versions for HelveticaNow, or accept the fallback stack silently.

**Issue 3d — Non-standard `Src:` capitalization in `@font-face`**

All 10 `@font-face` blocks use capital `Src:` instead of lowercase `src:`:
```css
@font-face {
  font-family: 'HelveticaNow_Regular';
  Src: url("...") format('truetype'); /* ← invalid capitalization */
}
```

CSS property names are technically case-insensitive per spec, and browsers tolerate this, but it is non-standard and will fail strict CSS validators. Some email preprocessing tools that normalize CSS may drop the declaration.

**Issue 3e — Conflicting `text-size-adjust` declarations**

```css
* {
  -ms-text-size-adjust: 100%;
  -webkit-text-size-adjust: 100%;
  -ms-text-size-adjust: none;  /* ← overrides the 100% set two lines above */
  text-size-adjust: none;
}
```

`-ms-text-size-adjust` is declared twice with conflicting values (`100%` then `none`). The second declaration wins, disabling text size adjustment in IE/Windows Mail. The intent is likely `none` on WebKit (to prevent iOS auto-scaling) and `100%` on `ms`. Should be split:

```css
-webkit-text-size-adjust: none;
-ms-text-size-adjust: 100%;
text-size-adjust: none;
```

**Issue 3f — Off-black color values (`#000001`, `#00000F`)**

```css
border-top: 1px #000001 solid;  /* mobile CSS */
.dm-bg-black { background: #00000F !important; }
.dm-font-black { color: #000001 !important; }
```

These appear to be intentional Gmail/Apple Mail dark-mode workarounds (pure `#000000` can be overridden by client theming). If intentional, document them inline. If accidental, they are off-spec values that may cause subtle rendering differences on calibrated displays.
