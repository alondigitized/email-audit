## Technical Audit — Skechers "Customer Approved Sneakers" (2026-07-03)

### 1. Technical Summary

The email has a systemic HTTP-over-HTTPS image delivery problem across all hosted assets and a broken inbox-monitoring pixel. No unrendered merge tokens detected in the truncated source; compliance elements were not visible due to truncation.

---

### 2. Link & Tracking Issues

**Broken Return Path / Validity inbox-monitoring pixel**
The pixel src is missing its protocol:
```
src="pixel.app.returnpath.net/pixel.gif?r=964ce1dbf0dcef79cbad82c12fe25342701e4499"
```
Without `https://`, email clients interpret this as a relative URL and the request never fires. Inbox reputation monitoring data is silently lost for this send.

**26 click-redirect links not probed**
All product and CTA links route through `click.emails.skechers.com`. UTM parameter presence and link-rot cannot be confirmed without resolving those redirects.

**Three Krux/DMP beacons present**
`beacon.krxd.net` fires two user-match pixels (one SHA-256 hashed UID, one raw `subid`) plus one ad-impression pixel. The raw subscriber ID (`partner_uid=121173391`) is transmitted as plaintext in the impression URL alongside the campaign ID — no hashing.

**QA summary contradiction**
The automated QA block reports "100% pass rate, 0 issue(s), 0 warning(s)" immediately after listing 14 warnings. The summary line appears to reflect a different check scope or a reporting bug; the 14 warnings are real and should not be dismissed.

---

### 3. Rendering & Accessibility

**All image assets served over HTTP — not HTTPS**

Every content image comes from `http://image.emails.skechers.com/`:
- Logo: `http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/1/dde00662-169f-447d-b0e2-fc65f6c2290c.png`
- App Store badge, Google Play badge, social icons, Curbside/AfterPay/Find-a-Store icons — all HTTP

Gmail and Outlook.com proxy images through their own HTTPS CDN, which masks the issue in those clients. However, some enterprise and native clients block mixed-content image loads outright, and HTTP delivery is a sending-reputation signal for some mailbox providers.

The third-party pixel also uses HTTP:
```
src="http://www.ink1000.com/p/up/7076d8b15a776085/o.gif?mi_u=8107766165&..."
```

**Missing alt text**

Two images have no `alt` attribute:
- `o.gif` (ink1000 pixel) — acceptable for a tracking pixel, but should be `alt=""`
- `49468f73-4651-4af3-bea2-61d1ae5db486.png` — content image with no alt; screen readers skip it entirely

**`-webkit-text-size-adjust: none` applied globally**
```css
* { -webkit-text-size-adjust: none; }
```
This prevents iOS Mail from scaling small text to readable sizes, which is an accessibility regression for users who rely on system font scaling.

**Duplicate media query blocks**
`max-width: 375px` and `max-width: 640px` rules are declared twice with identical rule sets. A second `<style>` block re-declares `max-width: 480px` overlapping the 640px breakpoint. No rendering breakage, but increases parse weight and maintenance surface.

**Invalid `<meta content="...">` (no `http-equiv`)**
```html
<meta content="text/html; charset=utf-8" />
```
Should be:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
```
Without `http-equiv`, the charset declaration is invalid and some older clients may default to a different encoding.
