### 3. Rendering & Accessibility

**Issue 1 — Malformed `@font-face` `src` property (all 10 declarations)**

Every `@font-face` block uses a capitalized `Src:` instead of the spec-correct lowercase `src:`. CSS property names are case-insensitive per spec, but several older email client parsers (notably some Outlook WebView variants) treat unknown properties as no-ops, silently dropping the font load and falling back to system fonts.

```css
/* as written — invalid in strict parsers */
Src: url("https://braze-images.com/appboy/...") format('woff');

/* correct */
src: url("https://braze-images.com/appboy/...") format('woff');
```

Affects all 10 faces: `Futura_PT_Regular`, `Futura_PT_Medium`, `Futura_PT_Demi`, `Futura_PT_Bold`, `HelveticaNow_*` (6 weights).

**Issue 2 — `-ms-text-size-adjust` conflict in `*` selector**

The universal reset sets `text-size-adjust` twice in a single rule, with the second value overriding the first:

```css
*{
  -ms-text-size-adjust: 100%;   /* set */
  ...
  -ms-text-size-adjust: none;   /* immediately overridden — none wins */
  text-size-adjust: none;
}
```

`text-size-adjust: none` globally disables user-agent text scaling on all elements. This is aggressive and will suppress OS-level accessibility zoom in some Windows Phone / older Android WebView clients. The intended value is typically `100%`.

**Issue 3 — Images not visible in truncated source**

**Issue — Malformed charset `<meta>` tag**

```html

<!-- correct -->
```

The `http-equiv` attribute is absent. Without it, this tag is parsed as an unknown/no-op meta element; the charset declaration does not apply. Most modern clients infer UTF-8 from the HTTP `Content-Type` header, but older or misconfigured clients that rely on the meta tag may misinterpret character encoding, causing garbled rendering of special characters (e.g., trademark symbols, accented characters).
