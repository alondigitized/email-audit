### 3. Rendering & Accessibility

**Issue 1 — Missing `http-equiv` attributes on two meta tags:**
```html
<meta content="text/html; charset=utf-8" />        <!-- missing http-equiv="Content-Type" -->
<meta content="IE=Edge" />                          <!-- missing http-equiv="X-UA-Compatible" -->
```
Without `http-equiv`, these tags are ignored by parsers. The charset declaration won't be honored and IE compatibility mode won't activate.

**Issue 2 — Contradictory `text-size-adjust` in the `*` reset:**
```css
* {
  -ms-text-size-adjust: 100%;
  -webkit-text-size-adjust: 100%;
  -ms-text-size-adjust: none;   /* overrides the 100% above */
  text-size-adjust: none;
}
```
`-ms-text-size-adjust: none` is the winning declaration (last wins). This can cause Outlook/IE to suppress text scaling entirely rather than just preventing auto-resize. The intent is `100%`, not `none`.

**Issue 3 — `Src:` (capitalized) in all `@font-face` blocks:**
```css
@font-face {
  font-family: 'Futura_PT_Regular';
  Src: url("https://braze-images.com/...") format('woff');
}
```
CSS property names are case-insensitive per spec, but some older email rendering engines are strict. Lowercase `src:` is the safe standard.

**Issue 4 — `supported-color-schemes` declared in CSS `:root`:**
```css
:root {
  color-scheme: light dark;
  supported-color-schemes: light dark;  /* not a valid CSS property */
}
```
`supported-color-schemes` is only recognized as an HTML `<meta>` tag (already present in `<head>`). The CSS declaration is a no-op and creates an invalid property warning in strict parsers.

**Issue 5 — Font format coverage gaps:**
- Futura PT fonts: `.woff` only. No `woff2`, no fallback stack ordering. Email client support for remote `@font-face` is limited; `woff2` would improve coverage in Apple Mail.
- HelveticaNow fonts: `.ttf` only. TTF has the weakest email client support of the web font formats. Neither set declares a `format('woff2')` source.
