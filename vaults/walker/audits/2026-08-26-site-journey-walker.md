# Daily Journey: Walker Miles on www.skechers.com
**Score:** 2/10 (prev 2/10) · **Type:** Site journey · **2026-08-26**
## Full review
## 1. Executive Summary

I made it from the homepage all the way to a product I actually liked — a Slip-ins pair with Contour Foam — but the trip fell apart right where it counts. Login never actually logged me in, Add to Cart never actually added anything (the cart badge sat at 0 the whole time), and when I tapped "View Cart" I got a blank white screen. Search for "comfort shoes" pulled up women's shoes first. I never got to check out, and at my age, if I can't tell whether something's in my cart, I'm not trusting it with my credit card.

## 2. Business Impact Score (1-10)

**2/10** — same as yesterday, no real improvement. The men's category browsing and product page are genuinely good (slip-ins and walking shoes are front and center), but the cart is fundamentally broken and login silently fails. A shopper who gets this far and hits a blank cart page will not come back to try again — they'll call the store or just order from Hoka instead.

## 3. What's Working

- **Category navigation for my needs**: The Men > Shoes page leads with "Hands Free Slip-Ins," "Walking Shoes," and "Athletic Sneakers" tiles right up top — that's exactly the kind of shoe I'm shopping for, no digging required.
- **Product page clarity**: The slip-ins product page shows price, discount code, star rating with review count, and a clear "Hands Free Slip-ins" badge. Big readable text, no squinting needed.
- **Hamburger menu structure**: The Men flyout menu (Shoes, Shop by Activity, Comfort Technologies, Collections) has large, clearly spaced tap targets — easy to hit with a thumb.
- **Search relevance to the concept**: Typing "comfort shoes" did return comfort-styled shoes (GO WALK Arch Fit, Relaxed Fit) rather than irrelevant junk — the search engine understands the term even if gender filtering is off.

## 4. What's Weak

- **Login is broken or silent**: After tapping Login, the page looks identical to the homepage — still says "Login" in the header, no name, no account indicator. I have no idea if I'm signed in.
- **Add to Cart doesn't add to cart**: I picked a size and width (implied by the flow) and hit Add to Cart, but the cart icon still reads "0." Did it work? Did it not? There's no confirmation toast, no slide-out, nothing.
- **Cart page is completely blank**: Tapping the cart icon led to a totally blank white screen. Nothing. This is the single worst moment in the whole journey — if I can't see what I'm about to pay for, I'm closing the tab.
- **Pre-filled error messages on the size selector**: The Add to Cart screen shows "Please select a width" and "Please select a size" warnings in red before I've done anything wrong — that reads like something already broke, not like a helpful prompt.
- **Search results aren't personalized to me**: I'm a man browsing men's shoes, but "comfort shoes" search leads with two women's styles. If the site knows I was just looking at men's slip-ins, it should know better.
- **No arch support / cushioning callouts on search or category cards**: The stuff I actually care about — arch support, cushioning depth — isn't visible until I'm deep into a single product page.

## 5. Recommendations

1. **Fix the cart page rendering** — a blank white screen after Add to Cart is a hard stop for any shopper, let alone one who's already nervous about doing this on a phone. This should be priority one, full stop.
2. **Make Add to Cart give visible confirmation** — update the cart badge count immediately and show a brief confirmation (toast, slide-out panel, whatever) so I know the click worked.
3. **Fix login state persistence** — after tapping Login, either show me a real login form or reflect signed-in status in the header. Right now it looks like nothing happened.
4. **Gender-filter search by browsing context** — if I've been in Men's Shoes, weight "comfort shoes" results toward men's product first.
5. **Surface cushioning/arch-support badges on listing and search cards**, not just the full product page — that's the deciding factor for me before I even click in.

## 6. Bottom Line

The site knows what I want to buy — slip-ins, walking shoes, cushioned comfort — and gets me to the right product fast. But the moment it's time to actually buy, it falls apart: cart count never updates, and the cart page itself is blank. No score above a 2 or 3 is honest while checkout is this broken; the browsing experience doesn't matter if I can't complete a purchase.

## Technical Audit

## Technical Summary

Site runs on Salesforce Commerce Cloud (SFCC) — confirmed by `/on/demandware.static/Sites-USSkechers-Site/.../us-skechers-prod.js` in the Men category page source. The journey shows a mix of full document navigations (Homepage, Log In, Men category: TTFB 403–454ms) and much faster sub-100ms responses (Men>Shoes, Product detail, Add to Cart, Search: TTFB 24–29ms), consistent with client-side/XHR-driven transitions rather than full page reloads for those steps — worth confirming this doesn't mask real navigation TTFB in synthetic monitoring. The most notable infra-level finding is that the homepage and category pages load Google Tag Manager with `gtm_preview=env-1&gtm_auth=...&gtm_cookies_win=x` hardcoded into the script URL, which puts GTM into **Preview/Debug mode for production traffic**. Bot-mitigation (Kasada) fingerprinting calls are being rate-limited (429) repeatedly during the cart flow, and the cart page itself returned a 429 once.

## Accessibility

18 axe violations across 3 of 8 audited steps (Homepage, View Cart, Search).

- **Critical (2, Homepage):** `button-name` — buttons without discernible text; `aria-required-parent` — ARIA role used without required parent role container.
- **Serious (3):** `link-name` (Homepage) — links without discernible text; `document-title` and `html-has-lang` (View Cart) — the cart document is missing a `<title>` and the `<html>` element has no `lang` attribute.
- **Moderate (11):** repeated landmark issues on Homepage and Search — `landmark-main-is-top-level`, `landmark-no-duplicate-main`, `landmark-unique`, `landmark-complementary-is-top-level`, `region` (content not contained in a landmark), `heading-order`; View Cart additionally fails `landmark-one-main` and `page-has-heading-one` (no `<main>`, no H1).
- **Minor (2):** `aria-allowed-role` on Homepage and Search (invalid role value on an element).

The View Cart failures (`document-title`, `html-has-lang`, `landmark-one-main`, `page-has-heading-one`) as a cluster suggest the cart view may be rendering as a partial/fragment response or an atypical document context rather than a standard full-page render — this pattern is distinct from the landmark/heading issues seen elsewhere and should be verified against the raw cart page source.

## SEO

- `html-has-lang` and `document-title` missing on View Cart (see above) — beyond accessibility impact, a missing `<title>` is a hard SEO defect on any indexable URL; low priority if `/cart/` is `noindex`, but should be confirmed rather than assumed.
- Head markup on Homepage/Log In/Men category is dominated by 15+ third-party async tracking scripts (TikTok, Snapchat, Reddit, Meta, Bing, Quantum Metric, Monetate ×2, Taboola, Impact, Yahoo, PulseInsights, GTM ×2 destinations) ahead of/interleaved with core content in the served HTML — this doesn't block indexing (scripts are async) but increases HTML payload before crawlers reach primary content signals.
- Could not verify `<title>`, meta description, or canonical tags on Homepage/Log In/Men category from the provided samples — head content was truncated before these elements. Recommend re-checking full `<head>` directly.

## Performance

- TTFB is acceptable-to-elevated on full navigations: Homepage 454ms, Log In 403ms, Men category 403ms. These exceed the commonly cited ≤200ms "good" TTFB threshold for a first-party CDN-fronted storefront and warrant server/origin investigation (SFCC dynamic rendering + heavy synchronous cookie/consent script injection at the top of `<head>` are plausible contributors).
- Men>Shoes, Product detail, Add to Cart, Search all show TTFB in the 24–29ms range — too fast to be full-document server renders, indicating these steps are measuring client-side transitions/XHR rather than navigation TTFB. This is a measurement-scope issue for the audit methodology, not necessarily a site defect — LCP/CLS were not captured for any step, so real paint/layout-shift performance is unverified.
- LCP and CLS are unmeasured for all 8 steps — no performance verdict can be given on visual load completeness or layout stability; this should be re-run with a tool that captures paint timing.
- Homepage/category head blocks load 15+ third-party scripts (ads, pixels, analytics, personalization) via `async`, plus a synchronous Google Fonts loader (`webfontloader.js`) and two separate GTM containers (main + a `gtm/destination` variant) — this is a substantial third-party JS footprint that can delay LCP even though scripts are non-blocking, due to main-thread contention on load.
- **GTM Preview mode exposed in production**: the GTM script tag includes `gtm_preview=env-1&gtm_auth=7lRL-CECKNSv2w3ulidcfw&gtm_cookies_win=x`. If unintentional, this can serve unpublished/draft tag configurations to live users and adds unnecessary GTM debug overhead.

## Mobile Optimization

- A `--vh` CSS custom property is set inline via JS on `<html>` (`style="--vh: 6.64px"`), indicating a mobile viewport-height polyfill for browser-chrome resize issues — standard pattern, no issue found.
- Viewport `<meta>` tag was not present in the truncated HTML samples provided, so responsive viewport configuration could not be verified from this data.
- No mobile-specific console/network errors distinct from the desktop-shared issues below were observed.

## Console & Network Errors

- **429 (Too Many Requests) — repeated, 5 occurrences**: `https://www.skechers.com/.../fp?x-kpsdk-v=j-1.2.726` — this is a Kasada bot-detection fingerprinting endpoint being throttled by its own backend during the Add to Cart → View Cart flow. One 429 also hit `/cart/` directly, meaning the bot-protection layer rate-limited an actual page navigation, not just a background telemetry call.
- **CORS failure**: `https://web-assets.stylitics.com/style.css` blocked — response lacks `Access-Control-Allow-Origin` for `https://www.skechers.com`. This third-party stylesheet (Stylitics outfit/styling widget) fails to load, likely breaking that widget's presentation.
- **net::ERR_FAILED**: one unresolved network failure, consistent with the CORS-blocked stylesheet above.
- **Unsupported Summarizer API language** (4 occurrences): Chrome's experimental on-device Summarizer API (`window.ai`/Gemini Nano) is being invoked with an unsupported `language` parameter and aborting. Non-fatal, but indicates first- or third-party script is calling an experimental browser API without checking language support first, generating console noise on every affected page load.

## Recommendations

1. Investigate the hardcoded `gtm_preview`/`gtm_auth` parameters on the production GTM script tag — confirm whether preview/debug mode is intentionally live for all visitors; if not, remove it.
2. Investigate the repeated 429s from the Kasada fingerprint endpoint and the single 429 on `/cart/` — determine whether legitimate mobile traffic is being throttled by bot-mitigation rate limits during checkout, which would directly harm conversion.
3. Fix the Stylitics stylesheet CORS failure (`Access-Control-Allow-Origin` missing) so the styling widget's CSS loads.
4. Add `lang` attribute and a non-empty `<title>` to the View Cart document; add a top-level `<main>` landmark and an H1.
5. Resolve the ARIA/landmark violations on Homepage and Search (duplicate/non-top-level `main` and `complementary` regions, elements outside any landmark, invalid `role` values) — likely a shared header/footer or third-party widget markup issue given the overlap across pages.
6. Add discernible accessible names to the flagged buttons and links on Homepage.
7. Guard the experimental Summarizer API call behind a language/capability check to stop the console errors.
8. Re-run performance capture with a tool that reports LCP/CLS, and separate full-navigation TTFB from client-side transition timing to get an accurate picture of real page-load performance.
