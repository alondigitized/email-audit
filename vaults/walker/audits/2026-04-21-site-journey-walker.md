## 1. Executive Summary

Look, I've been shopping Skechers for years and I'm a Plus member. I just want to find my Slip-ins, see my deal, and check out. Today's visit had some real bright spots in the middle — the Men's menu was clean, I found Slip-ins fast, and the product page showed me my BOGO deal clearly. But the homepage ignored me again, the login experience was invisible, and the cart page was completely blank. A white screen where my cart should be. That's not a minor bug, that's a brick wall right before the finish line.

- **Size grid is tappable.** The size buttons on the Add to Cart screen are big, evenly spaced squares. Even with stiff fingers at 62, those are easy to hit.
- **"ADD TO CART" button is enormous and sticky at the bottom.** Can't miss it. That's good design.
- **BOGO deal is persistent** — it shows in the top banner on nearly every page. I kept seeing it and that matters to a price-conscious shopper like me.
- **Search found 1,002 results for "slip in"** — the catalog is there.

## Technical Audit

## Technical Summary

The Skechers mobile journey has three categories of active breakage: a bot-detection endpoint returning HTTP 429 during normal user sessions (including on the cart page), a CORS misconfiguration blocking a third-party style dependency, and 4 critical ARIA violations in the axe scan. LCP and CLS were not captured for any step, leaving Core Web Vitals assessment incomplete. The page shell carries a heavy third-party script payload (~20+ async tags in `<head>`) that is the primary risk to LCP.

---

## Accessibility

**Critical (WCAG 2.1 Level A failures):**

| Violation | Page | Impact |
|---|---|---|
| `aria-required-parent` | Homepage | Orphaned ARIA role children — screen readers will skip or misread the structure |
| `aria-required-children` | View Product | Role container missing required child roles |
| `aria-valid-attr-value` | View Product | Malformed ARIA attribute values — AT may throw errors or ignore element |
| `button-name` | View Product | Unnamed buttons — completely inaccessible to screen readers |

**Serious:**
- `link-name` (Homepage): anchor tags with no discernible text (likely icon-only links with no `aria-label`)
- `aria-dialog-name` (View Product): modal dialogs have no accessible name — screen readers cannot announce what dialog opened
- `aria-input-field-name` (View Product): unlabeled input fields
- `link-in-text-block` (Men's Shoes): color-only link differentiation fails WCAG 1.4.1
- `color-contrast` (View Product): text fails WCAG AA minimum 4.5:1 ratio

**Moderate (structural landmark issues, all pages):**
- `landmark-no-duplicate-main`: multiple `<main>` elements in DOM — likely caused by SPA rendering leaving stale markup
- `landmark-main-is-top-level`: `<main>` nested inside another landmark
- `landmark-complementary-is-top-level`: `<aside>` not at top level
- `heading-order`: h-level skip (e.g., h1 → h3)

32 total violations. 4 are critical Level A failures.

## Mobile Optimization

- `--vh: 6.640000000000001px` is set inline on `<html>` via JavaScript as a workaround for the iOS Safari 100vh bug. The floating-point value (`6.640000000000001`) suggests this is computed as `window.innerHeight / 100` without rounding — use `parseFloat(...toFixed(2))` to avoid sub-pixel drift.
- No `<meta name="viewport">` tag is visible in the captured fragments (they are truncated), but the `--vh` logic implies it exists. Verify `width=device-width, initial-scale=1` is present.
- `vice-managed-src` is a TrustArc consent attribute that defers script `src` assignment until consent fires. Scripts managed this way will not load until the consent banner is dismissed, which is correct consent-management behavior but can delay analytics initialization and potentially affect A/B testing (Monetate).

## Console & Network Errors

**HTTP 429 — KPSDK fingerprinting endpoint (5 hits):**
```
/149e9513-01fa-4fb0-aad4-566afd725d1b/2d206a39-8ed7-437e-a3be-862e0f06eea3/fp?x-kpsdk-v=j-1.2.381
```
This is the Kasada bot-protection SDK polling its fingerprint endpoint. Five 429s during a single mobile session means the client is being rate-limited by its own bot-detection layer. Likely causes: the mobile test session exceeded the per-IP or per-session polling budget, or the SDK version (`j-1.2.381`) is retrying too aggressively. This is a functional regression risk — Kasada is also the gate for `/cart/`, which returned a 429.

**HTTP 429 — Cart page:**
```
429 https://www.skechers.com/cart/
```
The cart page itself is returning 429. If Kasada challenges are failing (because the fingerprint endpoint is also 429'd), the cart will be blocked for real users who exceed the polling threshold. This is a checkout funnel break.

**CORS — Stylitics stylesheet:**
```
Access to CSS stylesheet at 'https://web-assets.stylitics.com/style.css?...'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header
```
The browser is fetching this stylesheet via `XMLHttpRequest` (confirmed by the second error line showing an XHR attempt), not via a `<link rel="stylesheet">` tag. `<link>` tags are not subject to CORS. The Stylitics integration is programmatically injecting this CSS via `fetch()` or `XMLHttpRequest`, which requires the Stylitics CDN to return `Access-Control-Allow-Origin: https://www.skechers.com`. Either Stylitics needs to add that header, or the integration code should use `<link>` injection instead of XHR. The styled component (the "hotspots" widget) will render without its styles.

## Recommendations

1. **Fix cart 429 immediately.** The `/cart/` 429 is a checkout funnel break. Investigate whether Kasada's bot-detection is incorrectly classifying the mobile test user-agent or if the fingerprint polling cadence exceeds rate limits. Work with Kasada support on the `j-1.2.381` SDK configuration.

2. **Resolve Stylitics CORS.** Change the Stylitics widget integration to inject the stylesheet via a `<link>` DOM element rather than XHR/fetch. This is a one-line fix on the integration side and requires no changes to the Stylitics CDN.

3. **Fix the 4 critical ARIA violations before next release.** Priority order: `button-name` (View Product) → `aria-required-parent` (Homepage) → `aria-required-children` (View Product) → `aria-valid-attr-value` (View Product). These are Level A failures.

4. **Instrument LCP and CLS.** All 8 steps are missing LCP and CLS. Add `PerformanceObserver` for `largest-contentful-paint` and `layout-shift` entries, or enable CrUX / Real User Monitoring. Without these, Core Web Vitals status is unknown.

5. **Remove duplicate script tags.** `tags.creativecdn.com/dhGobFICKSkk6J9nvQPw.js` fires twice on Men's Category. Audit the GTM container for duplicate tag triggers.

6. **Add Product structured data** to PDP pages for rich result eligibility (Product name, price, availability, image, brand).

7. **Round the `--vh` value.** Change the JS that writes `--vh` to use `.toFixed(2)` before setting the CSS property to avoid sub-pixel drift.
