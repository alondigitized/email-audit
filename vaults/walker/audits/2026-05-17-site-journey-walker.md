## 1. Executive Summary

I spent time walking through Skechers.com on my phone today. The good news: they know what I want — Hands Free Slip-ins, arch support, max cushioning — and they put it right in my face from the second I land. The menu is clean, the product page is solid, and that BOGO deal is hard to miss. But then I went to check my cart and hit a completely blank white page. Nothing. After all that work finding the right shoe, picking my size — a blank screen. That's not a small glitch, that's a door slamming in my face right at the register. Search also served me women's shoes first when I typed "comfort shoes," and I never actually saw a login screen — it seems like the site just skipped past that. These aren't polish issues. They're purchase-blocking problems.

## 5. Recommendations

1. **Fix the cart page immediately.** This is the highest-priority issue on the entire site. A blank cart is a conversion killer. Run a smoke test after every deploy. This should never reach production.

2. **Show a login confirmation.** After login, flash a "Welcome back, Walker" banner or show my name in the account icon. I need to know the site knows me. Right now I feel like a stranger even after signing in.

3. **Filter search results by the logged-in user's gender.** If I'm a man and I search "comfort shoes," men's results should come first. This is table-stakes personalization. If I'm not logged in, use recent browsing history. I should not have to add "men's" to find men's shoes.

4. **Wrap or scroll-indicate the filter chips row.** A subtle "..." or a visual gradient on the right edge of the chip row would signal there's more to tap. Or wrap to two lines. Don't let any option get cut off.

5. **Add a loyalty/points nudge near checkout.** At the add-to-cart or cart stage, tell me how many points I'm earning on this purchase. That's what keeps me coming back over going to Hoka next time.

## Technical Audit

## Technical Summary

Eight-step mobile journey on skechers.com (Salesforce Commerce Cloud / Demandware). TTFB is healthy across most pages; View Cart spikes to 145ms. The cart page has two serious WCAG failures and returns a 429, blocking checkout. The bot-detection fingerprinting service (KapSolve) is rate-limiting itself across the session. Third-party script count is extremely high. LCP and CLS values were not captured and cannot be evaluated.

---

## Accessibility

**Critical (1)**
- `aria-required-parent` — Homepage. An element with an ARIA role that requires a parent container (e.g., `role="option"` without a `role="listbox"` ancestor) is orphaned. Broken for screen readers; programmatic focus order is incorrect.

**Serious (2) — View Cart only**
- `document-title` — The View Cart "page" has an empty or absent `<title>`. Strongly suggests the cart is rendered inside an `<iframe>` or a client-side modal that injects a new `document` context without setting `document.title`.
- `html-has-lang` — Same root cause: the injected document context lacks `lang="en"` on its `<html>` element. Screen readers will guess the language. Both violations are WCAG 2.1 Level A failures.

**Moderate (8)**
- Homepage: `heading-order`, `landmark-complementary-is-top-level`, `landmark-main-is-top-level`, `landmark-no-duplicate-main`, `landmark-unique`, `region` — classic SFCC template landmark nesting issues; `<aside>` and `<main>` are not direct children of `<body>`.
- Search: `landmark-complementary-is-top-level`, `landmark-unique`, `region` — same pattern.

**Minor (1)**
- `aria-allowed-role` — Homepage. An element has a `role` value that is not permitted for that HTML element.

---

## SEO

- **`<html lang="en">`** is present on Homepage, Log In, and category pages — no issue there.
- **View Cart is missing `<title>`** — if cart is ever crawlable or shared via URL, Google will have no title signal. Not typically a ranking issue (carts are noindex'd) but confirms the iframe/document-context hypothesis.
- The `--vh` CSS custom property is injected inline on `<html>` via JS at runtime (`style="--vh: 6.64px"`). This is a JS-dependent viewport fix; if Googlebot renders the page with a different viewport, layout may shift.
- No canonical, structured data, or meta issues are visible in the truncated HTML, but the truncation prevents full verification.

## Mobile Optimization

- **`--vh` viewport hack** — `style="--vh: 6.64px"` on `<html>` is a JS-computed 1vh unit to work around iOS Safari's collapsing address bar. Common but means any layout that uses this variable is JS-dependent; without JS the viewport height is wrong.
- **WebFont Loader v1.6.28** from cdnjs — loads Mulish in 6 weights (n3–n8). The `wf-active` class appears on `<html>` before the font files finish, which could mask FOUT/FOIT issues. Using a CDN-hosted font loader adds a cross-origin DNS lookup and an additional script execution round-trip on mobile networks.
- No `<meta name="viewport">` visible in the truncated HTML samples, but its absence would cause major layout issues so it is almost certainly present — cannot confirm without full source.

## Console & Network Errors

**HTTP 429 — KapSolve bot fingerprinting endpoint (5 requests)**
```
/149e9513-01fa-4fb0-aad4-566afd725d1b/2d206a39-8ed7-437e-a3be-862e0f06eea3/fp?x-kpsdk-v=j-1.2.412
```
KapSolve (now part of Akamai Bot Manager) is rate-limiting its own fingerprinting probe. This is a misconfiguration in the bot protection rate-limit rules — the `/fp` endpoint is being counted against the same throttle bucket as regular traffic. The `x-kpsdk-v=j-1.2.412` parameter identifies the JS SDK version; 429s here mean KapSolve cannot attest the session as human, which can propagate downstream as false-positive bot blocks on real users.

**HTTP 429 — `/cart/`**
The cart page itself returns 429. This is the highest-severity issue in the session: a real user hitting the cart would receive a rate-limit error from their own checkout endpoint. Likely caused by automated test traffic (this audit run) triggering the same bot rules, but if this fires for real users it is a direct revenue blocker.

**CORS block — Stylitics stylesheet**
```
https://web-assets.stylitics.com/style.css?base=control&theme=skechers&version=8a49290ac7
```
`Access-Control-Allow-Origin` header is absent on the Stylitics CDN response for this stylesheet. The browser blocks it. Stylitics (outfit/complete-the-look widget) will render unstyled or broken. This is a Stylitics CDN configuration issue — the vendor needs to add `Access-Control-Allow-Origin: https://www.skechers.com` (or `*`) to that asset's response headers.

**`net::ERR_FAILED` (1)**
One unidentified resource failed at the network level (no URL captured). Could be a preconnect hint to a host that refused the connection, or a resource behind the 429 wall.

## Recommendations

**P0 — Fix immediately**
1. **Cart 429**: Investigate rate-limit rules for `/cart/`. Bot protection throttle buckets must exempt authenticated or session-cookie-bearing requests from the same strict limits applied to unauthenticated probes. Work with Akamai/KapSolve support on allowlist rules for the cart path.
2. **View Cart `<title>` + `lang`**: Whichever mechanism renders the cart (iframe, modal, SPA route) must set `document.title` and ensure `<html lang="en">` is present in that document context. If it is an iframe, both attributes must be set on the iframe's `srcdoc` or the loaded URL's `<html>`.

**P1 — Fix this sprint**
3. **Stylitics CORS**: File a ticket with Stylitics to add `Access-Control-Allow-Origin` to `web-assets.stylitics.com`. Confirm the header is present in staging before deploying new Stylitics SDK versions.
4. **KapSolve 429 on `/fp`**: The fingerprinting endpoint is inside the bot-protection perimeter — its own requests should be on an internal allowlist. Escalate to Akamai Bot Manager account team; this is a configuration issue on their side.
5. **`aria-required-parent` (Critical)**: Audit the Homepage for elements with child-only ARIA roles (e.g., `role="option"`, `role="row"`, `role="cell"`) and ensure they are wrapped in the correct parent role container.

**P2 — Next quarter**
6. **Duplicate script injection**: Deduplicate `dhGobFICKSkk6J9nvQPw.js` and `ytc.js` — GTM is likely firing them twice due to misconfigured trigger rules or duplicate tags in the GTM container.
7. **Capture LCP and CLS**: Re-run audit with a tool that captures these (Lighthouse, WebPageTest, or CrUX). TTFB alone is not sufficient for Core Web Vitals compliance.
8. **Script audit**: 22+ third-party scripts is unusually high. Consolidate analytics vendors through GTM where possible. Remove any decommissioned tags. Each additional `<script>` on mobile adds DNS, TCP, and JS parse overhead.
