- **"NEW NEW NEW" as the preheader** — I saw that before I even opened the email. It told me nothing and looked like something went wrong with the software.

- **Same playbook, again** — DSW sent me a nearly identical BOGO sandal email yesterday, and the day before that. The cadence has worn thin.

### 1. Technical Summary

Email is built on Braze, uses XHTML 1.0 Transitional, and includes dark-mode and mobile breakpoint support. Several minor but concrete CSS and meta-tag errors are present; the truncated source prevents full assessment of compliance, UTM coverage, and merge-token resolution.

### 2. Link & Tracking Issues

**Cannot fully assess** — HTML source is truncated before link/CTA elements. The following is confirmed from what's visible:

- Font assets are served from `braze-images.com`. If that CDN goes down or blocks external requests in a corporate mail client, all custom fonts fail silently (fallback fonts take over — acceptable, but worth monitoring).
- No click-tracking redirect prefix is visible in the truncated head; cannot confirm ESP wrapping is applied to all CTAs without the body.

---

### 3. Rendering & Accessibility

**Confirmed issues:**

1. **Missing `http-equiv` attributes on two meta tags:**
   - `<meta content="text/html; charset=utf-8" />` — should be `<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />`
   - `<meta content="IE=Edge" />` — should be `<meta http-equiv="X-UA-Compatible" content="IE=Edge" />`
   Without `http-equiv`, these tags have no effect in legacy renderers.

2. **`Src:` (capital S) in all 11 `@font-face` blocks** — CSS property names are case-sensitive per spec. All declarations use `Src:` instead of `src:`. Most modern renderers ignore case, but it is technically invalid and will silently fail in strict parsers.

3. **`font-weight: normal` on Bold/Demi font variants** — all `@font-face` declarations set `font-weight: normal` regardless of the variant (Regular, Medium, Demi, Bold). The CSS font-matching algorithm uses the declared weight to select the correct face. Declaring all as `normal` means `font-weight: bold` rules in the email will trigger synthetic bolding rather than loading the actual Bold face.

4. **`-ms-text-size-adjust` declared twice with conflicting values in the `*` selector:**
   ```css
   *{ -ms-text-size-adjust: 100%; ... -ms-text-size-adjust: none; ... }
   ```
   The second declaration (`none`) silently overrides the first (`100%`) for IE/Edge. Likely unintentional — disabling text-size adjustment on all elements can hurt readability on high-DPI IE/Edge renders.

5. **`maximum-scale=1` in viewport meta** — prevents users from pinch-zooming on mobile. This is an accessibility violation under WCAG 1.4.4 (Resize Text). Standard email practice is to omit `maximum-scale` or set it to `5`.

6. **`supported-color-schemes: light dark` in CSS `:root` block** — this is not a valid CSS property. It is only valid as a `<meta name="supported-color-schemes">` tag (already correctly present in `<head>`). The CSS rule is a no-op and should be removed to avoid confusion.

7. **HelveticaNow fonts served as `.ttf`, Futura PT as `.woff` only** — neither uses `.woff2`. WOFF2 is ~30% smaller and supported in all modern email clients that support web fonts at all. Low priority, but increases load time on slow connections.
