# Skechers.com Mobile Journey Review
**Reviewer:** Walker Miles, 62 | **Date:** June 7, 2026 | **Yesterday's Score:** 4/10

---

## 1. Executive Summary

A mixed bag with one critical breakdown. The Men's nav menu is clean and comfort-friendly, the product page is legible, and the BOGO deal is hard to miss. But the homepage hero is aimed squarely at someone 30 years younger than me, the login step produced nothing visible, and the cart page loaded completely blank — meaning I couldn't complete a purchase if I'd wanted to. Search returned women's shoes when I never told it I was a woman. Skechers knows how to build a comfort product; the website doesn't always act like it knows who's buying one.

---

## 2. Business Impact Score: 4/10

No change from yesterday. The clean Men's menu is a mild bright spot, but the blank cart is a hard regression — you literally cannot buy anything if that screen stays white. That alone caps the score.

---

## 3. What's Working

**BOGO banner is impossible to miss.** Blue strip across the very top of every screen: "BOGO 50% OFF Applied at Cart." I like a deal upfront. No hunting required.

**Men's category menu is genuinely good.** Large text, full-width tap rows, good vertical spacing. "Hands Free Slip-ins," "Wide Fit," and "Extra Wide Fit" are all right there without drilling three levels deep. "Comfort Technologies" as a named category is exactly how I think — I want to know what's in the shoe, not just what it looks like.

**Hands Free Slip-ins listing page is solid.** Clear headline, 298 results, width filters (Wide Fit / Extra Wide Fit / Medium Fit) shown immediately as tappable pills. That's the right way to surface fit options for someone my age without burying them in a filter drawer.

**Product page is readable.** Name, price, promo, stars — all visible without zooming. The "Cozy Fit Kiroh" at $88 with the BOGO badge applied was clear. The one-review count is thin, but the layout itself is fine.

**ADD TO CART button is excellent.** Full-width, high-contrast blue, big enough to hit with a thick thumb. That's how a CTA should look on mobile.

---

## 4. What's Weak

**Homepage hero says nothing to me.** "GAME ON!" with flashy green, blue, and red tennis shoes — that's a college athlete's homepage. I'm 62, I want cushioning and arch support, and nothing above the fold speaks to that. Slip-ins are in the nav strip but they're just a text label competing with four others. If comfort is Skechers' core identity, it's not the first thing I see.

**Login produced no result.** Step 3 (Log In) shows the exact same homepage screenshot as Steps 1 and 2. No login modal, no redirect, no account screen — nothing changed. Either it failed silently or the capture missed it. Either way, the "Member Month! Earn 2X Points" banner still shows "Login" as if I'm a stranger throughout the whole journey. If I'm not recognized, the site isn't personalized to me at all.

**Cart page is completely blank.** Step 8 is a white screen. Not a loading spinner. Not an error message. Just white. If this is what a real shopper sees after adding a shoe, they're gone. This is the single most damaging finding in this review — a broken checkout wall.

**Search for "comfort shoes" led with women's results.** 1,478 results, and the first two I saw were both labeled "Women's." I never identified myself as female. If the site knows I'm male (or should, if I was logged in), this is a personalization failure. Even without login, "comfort shoes" on Skechers.com should surface men's options as a default or ask me.

**"Please select a size" error on Add to Cart screen.** The warning fired before I tapped anything. That's a premature validation message — it should only appear after I've tried to add without selecting. Small thing, but it reads as scolding.

**The hero and promotions feel age-agnostic at best.** "Spring into Summer Sale! 25% OFF Apparel" is the popup-dismissed version of the promo — not shoe-focused, not comfort-focused. I came for shoes, not a shirt.

---

## 5. Recommendations

1. **Fix the cart page immediately.** A blank cart is a purchase-killer. This is P0. No UX improvement matters if a shopper can't complete a transaction.

2. **Personalize search by gender.** If I'm logged in as a male account, filter search results to men's by default. If I'm a guest, at minimum show a gender prompt at the top of the results page. Leading with women's shoes is a trust-breaker.

3. **Replace or supplement the "GAME ON!" hero with comfort messaging.** A rotating hero with one panel dedicated to "Your feet, your rules — Hands Free Slip-ins for men" would speak directly to buyers like me.

4. **Confirm login actually works and surfaces account state.** If "Member Month" is the hook, the login flow needs to be visible and rewarded — show my name, my points balance, maybe a "Welcome back, Walker" line in the banner after sign-in.

5. **Suppress the "please select a size" warning until the user attempts to add to cart.** Don't yell at me before I've done anything wrong.

The bones are there. The Men's menu and product page are both comfortable to use on a phone. But three things kept this at a 4: the homepage doesn't speak to comfort shoppers, the login flow showed nothing, and the cart page is broken white. Until that cart renders, I'm cross-shopping at zappos.com — same BOGO math, working checkout.

**vs. Yesterday:** No improvement. The Men's nav menu may be the same as before, but a blank cart is a hard regression if it wasn't there yesterday. Score holds at **4/10**.

## Technical Audit

## Technical Summary

Skechers.com runs on Salesforce Commerce Cloud (SFCC/Demandware). Core navigation TTFBs are strong (26–38ms), consistent with CDN-cached responses. Three structural problems stand out: the Kasada bot-protection layer is rate-limiting its own fingerprint endpoint during the test session, the View Cart page renders with a broken document shell (no `<title>`, no `lang`), and a large third-party script inventory contains at least two duplicate tag loads. LCP and CLS data were not captured, leaving the most user-impactful vitals unassessed.

## Mobile Optimization

- **`--vh` CSS variable:** The page injects `--vh: 6.640000000000001px` via JavaScript as a viewport height shim. This is a known workaround for mobile Safari's dynamic toolbar behavior. The floating-point imprecision (`6.640000000000001px` vs. `6.64px`) is a minor JS math artifact but harmless.
- **No explicit `<meta name="viewport">` visible** in captured HTML samples. This is likely present but beyond the truncation point in `<head>`. Should be verified — SFCC themes standardly include it, but it must be confirmed present and not overridden.
- **No `preconnect` hints visible** for dominant third-party origins (Google, TikTok, Meta, Monetate) — only `dns-prefetch` for Monetate. On mobile networks, missing `preconnect` hints add handshake latency for every first connection.

## Console & Network Errors

**429 Rate Limiting — Kasada Bot Protection (5 of 6 network errors)**

All 429s target:
```
/149e9513-01fa-4fb0-aad4-566afd725d1b/2d206a39-8ed7-437e-a3be-862e0f06eea3/fp?x-kpsdk-v=j-1.2.443
```

This is the **Kasada KP SDK fingerprint endpoint**. The path structure (two UUIDs + `/fp`) is Kasada's client interrogation handshake. 429 responses mean Kasada's server is rate-limiting or rejecting the session — consistent with automated browser behavior during testing. However, if real users encounter this, Kasada is misclassifying them as bots and their fingerprint tokens will be invalid, potentially breaking downstream protected endpoints (including `/cart/`, which also returned 429).

**Root cause candidates:**
1. Test harness fingerprint matches a known bot signature → Kasada blocks token issuance.
2. Client-side retry loop on 429 is not backing off (the 6 repeated calls to the same endpoint with no variation suggest no jitter/backoff).

The `/cart/` 429 is likely downstream of a failed Kasada token — the cart endpoint requires a valid KP token and rejects sessions without one.

**CORS — Stylitics stylesheet (1 error)**
```
Access to CSS at 'https://web-assets.stylitics.com/style.css?base=hotspots&theme=skechers&version=777c217f34' 
blocked by CORS policy: No 'Access-Control-Allow-Origin' header
```
Stylitics (outfit inspiration widget) is failing to serve its stylesheet with CORS headers. This is a **third-party configuration issue on Stylitics' CDN**, not Skechers' server. Skechers should file a support ticket with Stylitics. The widget will render without styles as a fallback — functionally broken but non-blocking for checkout.

## Recommendations

**P0 — Fix immediately**

1. **View Cart document shell regression:** The `<html lang>` and `<title>` attributes are absent only on the cart page, indicating a broken SPA route transition or a separate cart template that bypasses the standard page shell. Identify whether this is a template inheritance gap in SFCC or a missing hydration step in the JS router, then patch the cart template to always emit `lang="en"` and a non-empty `<title>`.

2. **Kasada retry storm:** The client is making 6 identical calls to the `/fp` endpoint with no backoff on 429. Audit the Kasada SDK configuration — ensure `x-kpsdk-v=j-1.2.443` is current (version pinning may be the issue if Kasada rotated expected versions). If this fires for real users, cart access will silently fail.

**P1 — Fix in next sprint**

3. **Critical ARIA violation (Homepage):** `aria-required-parent` at critical severity breaks assistive technology navigation of the affected widget. Identify the component (likely a carousel or combobox) and wrap it in the required ARIA parent container.

4. **Duplicate script loads:** Yahoo YTC (`s.yimg.com/wi/ytc.js`) fires twice on Homepage/Login; CreativeSSP (`tags.creativecdn.com/dhGobFICKSkk6J9nvQPw.js`) fires twice on Men category. These are GTM tag configuration errors — two rules firing the same tag. Each duplicate doubles the tracking payload and wastes a network request on mobile.

5. **Stylitics CORS:** File a ticket with Stylitics to add `Access-Control-Allow-Origin: https://www.skechers.com` on their CDN for the `style.css` resource.

**P2 — Address for Core Web Vitals**

6. **Add `preconnect` for top third-party origins:** Promote `dns-prefetch` to `preconnect` for Google Tag Manager, Monetate, and QuantumMetric (the three heaviest third-party actors visible in the HTML). Each `preconnect` saves a full TLS handshake RTT on first resource load.

7. **Capture LCP and CLS:** The audit cannot assess Core Web Vitals without these values. Instrument RUM (Real User Monitoring) or run Lighthouse in mobile simulation mode to get LCP and CLS baselines. Given the third-party script density, LCP degradation on mid-tier mobile hardware is a realistic risk.

8. **Landmark structure audit (Homepage + Search):** The `landmark-no-duplicate-main` and nested `<aside>` violations appear across multiple templates, suggesting a systematic layout issue in the shared SFCC template. Fix the base template rather than patching individual pages.
