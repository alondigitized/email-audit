## Technical Audit — Adidas Colombia FIFA World Cup 26 Away Jersey

### 1. Technical Summary

Two confirmed broken-experience bugs: a malformed `href` that will 404 in all email clients, and a completely absent plain-text MIME part. Several images serve over HTTP, creating mixed-content blocks in secure clients, and a missing `http-equiv` attribute renders the charset meta tag non-functional.

---

### 2. Link & Tracking Issues

**[FAIL] Malformed href — relative path used as absolute URL**

The QA probe flagged an "unknown URL type" for the following href value:

```
/g/800af384-bc4e-41f3-ba94-0200289a759f?txn=8212d300-56e4-11f1-9d8c-6e9b95041fa3
```

This is a bare relative path with no host. Email clients have no base URL to resolve it against — the link will 404 or be silently dropped. The full tracking wrapper (`dv.adidas.com/o/800af384...`) is present in the outer redirect chain, but the inner `href` is the one the client follows. This appears to be a dynamic content rendering failure — the template likely expected a full URL from the personalization engine and received only the path fragment.

**[WARN] 29 tracking links unverified**

All 29 click-redirect links (domains: `click.comms.adidas.com`, `link.adidas.com`) were skipped during probing. Destination URLs and redirect chain health are unconfirmed.

---

### 3. Rendering & Accessibility

**[FAIL] `<meta charset>` tag missing `http-equiv` attribute**

```html
<!-- current — non-functional -->
<meta content="text/html; charset=UTF-8" />

<!-- correct -->
<meta http-equiv="Content-Type" content="text/html; charset=UTF-8" />
```

Without `http-equiv="Content-Type"`, the charset declaration is ignored by HTML 4.01 parsers. Clients that don't detect encoding automatically may misrender special characters (e.g., ™ symbol in subject line, accented characters in body copy).

**[WARN] HTTP image sources — 7 instances, all same asset**

`b0c011a2-d468-414b-a8a2-8595b3ec7b34.jpg` (alt: "arrow") is served 6× via:

```
http://image.link.adidas.com/lib/fe6515707c62007e7715/m/3/b0c011a2-...
```

Gmail, Outlook.com, and Apple Mail block mixed-content HTTP images when the surrounding message is loaded over HTTPS. The arrow asset will render as a broken image placeholder in those clients. Additionally, the tracking pixel:

```
http://click.comms.adidas.com/CI0/0102019e56720d0a-3ff1166a-...
```

is also HTTP-only, so open tracking will fail in secure clients.

**[WARN] 3 images missing `alt` text**

| Asset | URL fragment |
|---|---|
| `b89f1065-48c3-4e59-9035-701fd3a63f68.png` | `image.link.adidas.com` |
| `800af384-bc4e-41f3-ba94-0200289a759f` | `dv.adidas.com/o/...` (dynamic content) |
| `zEsxQBnaRZXfO-Kdeq_ZQHKxz...` | tracking pixel |

The first two are visible content images — missing `alt` breaks the experience for image-off rendering and screen readers. The tracking pixel `alt=""` is standard and acceptable; the others need descriptive text.

**[INFO] Duplicate `@font-face` declarations**

`AdihausDIN` (400, 700) and `AdineuePRO` (400, 600) are each declared twice across two separate `<style>` blocks. The second declarations shadow local font fallbacks identically. This is harmless but bloats the `<head>` and signals a templating assembly issue.

### 5. Compliance

**[FAIL] Plain-text MIME part absent**

QA confirmed: `Text version is 0 chars`. CAN-SPAM does not strictly require a text part, but its complete absence degrades deliverability scores (SpamAssassin penalizes HTML-only messages), and RFC 2822 best practice requires a `multipart/alternative` structure with a text fallback. Major ESPs (Postmaster Tools, Microsoft SNDS) treat zero-length text parts as a spam signal.

HTML source is truncated — footer not visible. Unsubscribe presence cannot be confirmed. Sender domain `us-news.comms.adidas.com` suggests a legitimate ESP setup; CAN-SPAM compliance likely present but should be verified against the full source.

**[INFO] `ROBOTS: NOINDEX, NOFOLLOW`**

Present and correct for email. Prevents web-archived versions from being indexed.

### 6. Email-to-Site Continuity

**[WARN] `<meta name="referrer" content="no-referrer" />`**

This suppresses the HTTP `Referer` header on all link clicks. Any destination page relying on `document.referrer` for attribution (common in analytics setups that fall back to referrer when UTM params are absent) will see direct traffic instead of email traffic.

UTM parameter presence on destination URLs cannot be confirmed because all 29 tracking links were skipped during probing. If UTM params are embedded inside the `link.adidas.com` redirect chain, the `no-referrer` meta won't affect them — but if any landing page uses referrer as a fallback, attribution will be lost.
