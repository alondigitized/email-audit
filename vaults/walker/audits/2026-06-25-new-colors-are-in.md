# New colors are in
**Score:** 8/10 · **Type:** Email audit · **2026-06-14**
## Executive summary

- I open this thing and HOKA's basically asking me to nod at new paint jobs. "Shift Into Neutral" is a clever line — I'll give them that — but the whole email is about colorways, and colorways are about dead last on my priority list when I'm shopping for shoes. What I care about is whether my arches are going to survive a trip to the grocery store and back. Not a word about cushioning, not a word about fit, not a word about whether these updated Solimare 2s are any easier on a wide foot. Just: hey, gray is in this season.
- The execution is clean though. Big hero shoe at the top, readable text without zooming, clear buttons. - The "Find Your Best Fit" quiz section at the bottom is actually the most useful thing in the email for someone like me — except they paired it with a photo of some kid doing parkour in neon shoes, which is not me and not my world. I'd mark this as read, not click it. Wouldn't forward it to anyone.

- Shoe names are right there under each image (Transport 2, Solimar 2) — I don't have to guess what I'm looking at
- Text is large and readable on a phone without pinching

## What's weak

- Zero comfort language in the entire email — no cushioning, no arch support, no "wide fit available," nothing I actually make a shoe decision on
- That "Find Your Best Fit" quiz section is a good idea buried under a photo of someone doing an aerial leap in neon green shoes — that is not my body, not my life
- $250 threshold for free shipping is steep; I can get one pair of HOKAs near that but it's not an automatic pull

- 4. **Add one callout per shoe about the key comfort feature** — "extra-cushioned heel," "zero-drop," whatever makes that model worth trying. Give me a reason to tap.

### 3. Rendering & Accessibility

**Duplicate `<meta name="viewport">` tag**
Two viewport declarations appear in `<head>`:
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
<meta content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=yes" name="viewport" />
```
Conflicting `maximum-scale=1` (first) vs `user-scalable=yes` (second). The second overrides the first in most parsers, but this is undefined behavior. Remove the first occurrence.

**Empty `<title>` element**
```html
<title></title>
```
Several email clients (Samsung Mail, some older iOS builds) surface the `<title>` value as a preview or tab label. An empty title degrades accessibility and fallback preview rendering. Set to the subject line or brand name.

**Missing `http-equiv` on charset meta**
```html
<meta content="text/html; charset=utf-8" />
```
Should be:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
```
Without `http-equiv="Content-Type"`, the charset declaration is ignored by the HTML parser — encoding is inferred from the HTTP `Content-Type` header instead. Safe in modern ESP delivery but technically malformed.

**Malformed CSS — missing numeric values in mobile media query**
```css
.nav_padding { padding-top:px !important; padding-bottom:px !important; }
.nav_border  { border-top:px solid ; }
```
Both rules have bare `px` with no number and `.nav_border` has no color value. These declarations are invalid and will be dropped entirely. If `nav_padding` / `nav_border` elements appear on mobile, they will render with browser defaults rather than intended values.

**Web fonts will not render in most email clients**
Five `@font-face` declarations load `TheFutureHOKA` variants from:
```
https://www.hoka.com/on/demandware.static/Sites-HOKA-US-Site/-/en_US/fonts/
```
Gmail (all versions), Outlook (Windows), and Yahoo Mail do not support `@font-face` in email. Verify that a system font fallback stack is defined on all `font-family` declarations; if not, affected clients will fall back to the browser/OS default serif or sans-serif.
