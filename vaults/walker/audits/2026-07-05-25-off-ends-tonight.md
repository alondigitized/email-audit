### 3. Rendering & Accessibility

**`http-equiv` missing on charset meta tag (confirmed bug):**
```html
<meta content="text/html; charset=utf-8" />
```
Missing `http-equiv="Content-Type"`. Without it, this tag is inert in XHTML/HTML4. Correct form:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
```

**`Src:` capitalized in all 10 `@font-face` declarations (confirmed bug):**
```css
Src: url("https://braze-images.com/...") format('woff');
```
CSS property names must be lowercase. Strict parsers (e.g., certain Outlook WebView builds) will silently drop the declaration. All 10 `@font-face` blocks are affected — both Futura PT and HelveticaNow families.

**Conflicting `-ms-text-size-adjust` in `*` rule (confirmed bug):**
```css
*{-ms-text-size-adjust: 100%; ... -ms-text-size-adjust: none; text-size-adjust: none}
```
The property is declared twice in the same rule — `100%` then `none`. The second value wins, leaving `-ms-text-size-adjust: none` as the effective value on IE/Windows Mobile, which disables text scaling rather than preventing zoom-inflate. Additionally, `text-size-adjust: none` on `*` globally suppresses user-initiated text scaling — an WCAG 1.4.4 (Resize Text) concern.

**HelveticaNow fonts served as TTF only:**
The four newer HelveticaNow variants (`689df75b*` file IDs) include only `format('truetype')` with no WOFF fallback, while the Futura PT variants correctly serve WOFF. TTF downloads are larger (~2–3×) and render worse on Windows where WOFF is standard. Low impact since most email clients ignore web fonts entirely, but inconsistent with the existing Futura approach.

**Near-black dark mode colors appear intentional but warrant documentation:**
```css
.dm-bg-black { background: #00000F !important; }
.dm-font-black { color: #000001 !important; }
```
Likely intentional (avoids Gmail/Apple Mail true-black override bugs), but should be documented in the template spec to avoid future "bug" reports.
