### 3. Rendering & Accessibility

**`http-equiv` missing on two critical `<meta>` tags — these directives are non-functional as written:**

```html
<!-- Bug: missing http-equiv="Content-Type" -->
<meta content="text/html; charset=utf-8" />

<!-- Bug: missing http-equiv="X-UA-Compatible" — IE rendering directive silently ignored -->
<meta content="IE=Edge" />
```

Correct forms:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```

**`Src:` (capital S) in all 11 `@font-face` blocks** — the CSS `src` property must be lowercase. Most email clients are tolerant of this, but strict parsers (some Outlook WebView variants) may drop the rule, causing fallback font cascade.

```css
/* Appears in every @font-face block: */
Src: url("https://braze-images.com/appboy/...") format('woff');
/* Should be: */
src: url("https://braze-images.com/appboy/...") format('woff');
```

**`maximum-scale=1` suppresses user zoom (WCAG 1.4.4):**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```
This is common email practice to prevent iOS auto-zoom but fails WCAG 2.1 Success Criterion 1.4.4 (Resize Text). Low risk in email context, but worth flagging.

**`color-scheme` declared twice** — once in `<meta>` and again in the CSS `:root` block. The duplication is harmless but adds dead weight:
```html
<meta name="color-scheme" content="light dark" />          <!-- head -->
<meta name="supported-color-schemes" content="light dark" />
```
```css
:root { color-scheme: light dark; supported-color-schemes: light dark; }  /* body CSS */
```

**Font format inconsistency** — Futura PT fonts load `.woff`; Helvetica Now fonts load `.ttf`. TTF is larger and less supported in webmail (Gmail, Outlook.com). Both will fall back to system fonts, but `.woff` is the correct target for email.
