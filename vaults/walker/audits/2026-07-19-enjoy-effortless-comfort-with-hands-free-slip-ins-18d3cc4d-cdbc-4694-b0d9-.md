It didn't stop me from opening because I recognized the sender and liked the subject, but it chips away at the professional impression every single time.

## Technical Audit

## Technical Audit — Skechers "Enjoy effortless comfort with Hands Free Slip-ins"

---

### 1. Technical Summary

The email's primary technical risk is pervasive use of HTTP (non-HTTPS) image sources across the entire `image.emails.skechers.com` CDN, which will trigger mixed-content blocking or image suppression in modern clients. A secondary concern is a protocol-relative third-party pixel that may resolve inconsistently across clients.

---

### 2. Link & Tracking Issues

**26 click-redirect links skipped** — all outbound links route through `click.emails.skechers.com` (Salesforce Marketing Cloud redirect domain); destination URLs and UTM parameters could not be probed.

**Protocol-relative Return Path pixel** — the inbox placement beacon uses a bare hostname with no scheme:
```
src="pixel.app.returnpath.net/pixel.gif?r=964ce1..."
```
Without `https://`, resolution is client-dependent. Some clients will treat this as a relative path (broken); others inherit the document protocol (undefined in email). Should be `https://pixel.app.returnpath.net/...`.

**Third-party user-match beacons** — two Krux/Salesforce DMP calls fire on open:
```
beacon.krxd.net/1x1_usermatch.gif?partner=LprH63a7_sfmc_100007688_sha25&partner_uid=<SHA256_HASH>
beacon.krxd.net/1x1_usermatch.gif?partner=LprH63a7_sfmc_100007688_subid&partner_uid=121173391
```
The `_subid` call exposes a plain numeric subscriber ID (`121173391`) alongside the hashed email. If the hashed value is a SHA-256 of the email address (suggested by `_sha25` suffix), pairing these two in one send weakens pseudonymization.

**ink1000.com pixel over HTTP** — a third-party open tracker fires over cleartext:
```
src="http://www.ink1000.com/p/up/7076d8b15a776085/o.gif?mi_u=8107766165&mi_ecmp=..."
```
No alt text, no HTTPS. Will be blocked by Gmail and Apple Mail.

---

### 3. Rendering & Accessibility

**All CDN images served over HTTP** — every image sourced from `image.emails.skechers.com` uses `http://`, not `https://`. Affected images include the logo, product hero, app store badges, social icons, and footer icons (14 flagged by QA). Gmail and modern Apple Mail block HTTP image sources, causing a blank email for users in default "load images" mode.

```
http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/1/dde00662-...png  (logo)
http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/11/49468f73-...png  (missing alt)
```

**Missing alt text on two images**:
- `o.gif` (ink1000 pixel) — no alt, no `role="presentation"`
- `49468f73-4651-4af3-bea2-61d1ae5db486.png` — not identifiable as decorative; no alt text

**`maximum-scale=1` in viewport meta** — prevents user-initiated zoom on mobile, a WCAG 1.4.4 violation:
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```

**`-webkit-text-size-adjust: none` applied globally** via `* {}` — suppresses OS-level font scaling for users with visual impairment settings. Should be scoped to `body` or removed.

**Duplicate responsive CSS blocks** — identical rules are declared twice (once for `max-width: 375px`, once for `max-width: 640px`), plus a third `<style>` block in `<body>` targeting `max-width: 480px` with overlapping rules. This adds ~2 KB of redundant CSS and creates unpredictable specificity in clients that partially support media queries.

**Mobile/desktop visibility toggle** — the pattern defaults `desktop-content { display: none }` in global CSS and reverses with a `min-width: 768px` media query. Email clients that strip `<style>` blocks (notably older Outlook via Word renderer) will permanently hide desktop content.
