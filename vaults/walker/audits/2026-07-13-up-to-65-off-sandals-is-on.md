# Up to 65% off sandals is on!
**Score:** 7/10 · **Type:** Email audit · **2026-07-13**
## Executive summary

- Tenth time DSW's been in my inbox this week — and to their credit, they at least changed the playbook. Gone is the same ten-dollar/fifteen-dollar-off number that's been pinging me since Monday. This one's a proper sale: 65% off sandals, starting at $39.99. No argument with the offer. The problem is every photo in this email is a woman — strappy jeweled sandals, platform slides, wedge heels. The size grid at the bottom shows women's sizes 5 through 9. The button literally says "Shop All Women's." I am a 62-year-old man who would like a pair of shoes that don't make my arches scream by noon. This email has nothing to do with me.
- I'd mark it read without clicking. That said, I do have a wife, and I might forward it to her. That's the only action DSW is getting out of me here.

## What's working

- **Crystal-clear offer, right at the top.** "Up to 65% off" and "$39.99 starting price" — I knew the deal without reading a sentence. That's how it should work.
- **Clean layout, no broken images.** Logo, headline, offer, product, CTA — my eyes went exactly where they were supposed to.
- **Buttons are easy to tap.** "SHOP DSW SANDALS" has good size for a phone screen. Nothing to squint at or miss-tap.
- **Campaign makes seasonal sense.** Mid-July sandal sale is logical. I'm not confused about why I'm getting this.

## What's weak

- **100% women's — I don't exist in this email.** Models are women, sizing is women's (5–9), CTA says "Shop All Women's." Not a single men's product or signal anywhere.
- **"You *NEED* these sandals" in the preview.** Asterisks around NEED feel like someone trying too hard. I don't need an email to tell me what I need.
- **No comfort story whatsoever.** Not one word about arch support, cushioning, or how the shoes actually feel. For a shoe brand, that's a miss even if it were for men.
- **Cadence is still a problem.** This is roughly the tenth DSW email since Monday. Even with a new creative direction, my thumb is drifting toward Unsubscribe with each send.

## Recommendations

- 1. **Segment men out of this send — or add a men's module.** A single "Shop Men's Sandals" row at the bottom turns this from irrelevant to relevant for half their subscriber base in about two seconds. DSW sells men's shoes. Use that.
- 2. **Lead the preview with the discount, not an instruction.** "65% off — sandals from $39.99" tells me more than "You *NEED* these sandals."
- 3. **Put one comfort word in the hero copy.** "Cushioned," "supportive," or even "all-day wear" next to the price does real work for older shoppers who care how shoes feel.
- 4. **Add a deadline.** 65% off is a compelling number, but "ends Sunday" or "this weekend only" would get me moving instead of waiting.
- 5. **Pull back on email volume.** At ten sends in a week, DSW is training subscribers to ignore them.

### 3. Rendering & Accessibility

**`http-equiv` missing on two `<meta>` tags:**
```html
<!-- As written — missing http-equiv: -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=Edge" />

<!-- Should be: -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```
Both tags are no-ops as written. The charset declaration silently falls back to client defaults; the IE compat directive is ignored entirely.

**Non-standard `Src:` property in all `@font-face` blocks:**
```css
@font-face {
  font-family: 'Futura_PT_Regular';
  Src: url("...") format('woff');  /* ← capitalized S */
}
```
CSS property names are case-insensitive per spec, but several strict CSS parsers and some email-specific renderers reject non-lowercase property names. All four Futura and six HelveticaNow blocks are affected.

**`-ms-text-size-adjust` conflict in universal selector:**
```css
/* In the same rule block: */
*{ -ms-text-size-adjust: 100%; ... -ms-text-size-adjust: none; }
```
The `none` value overrides the preceding `100%` declaration. `none` disables text scaling on Windows Phone/IE Mobile — the intent appears to be `100%` (lock to declared size). Depending on cascade order this may render as the overriding `none`, which suppresses user text scaling.

**Font format efficiency:**
- Futura PT: `.woff` only (no `woff2` fallback). woff2 is ~30% smaller and supported in all modern email clients that support web fonts.
- HelveticaNow: `.ttf` only. TTF is the least compressed format; woff/woff2 is preferred.

**`supported-color-schemes` in `:root` CSS block:**
```css
:root { supported-color-schemes: light dark; }
```
`supported-color-schemes` is not a valid CSS property — it is only meaningful as a `<meta name="supported-color-schemes">` tag (which is correctly present). The `:root` declaration is a no-op and can be removed.
