## Technical Audit

## 1. Technical Summary
The email has one QA-confirmed broken-personalization defect (empty greeting) and several infrastructure problems in the markup: two `http://` images, a scheme-less tracking pixel, and incomplete `<meta>` tags. The HTML source was truncated, so footer, unsubscribe, and link-level checks could not be verified.

## 2. Link & Tracking Issues
- **Scheme-less pixel URL:** `<img src="pixel.app.returnpath.net/pixel.gif?r=964ce1db…" width="1" height="1" />` has no `http(s)://`. Clients resolve it as a relative path, so the request fails and the Return Path/Validity seed-tracking pixel never fires. It also has no `alt`.
- **Insecure tracking pixel:** `http://www.ink1000.com/p/up/7076d8b15a776085/o.gif?mi_u=8107766165&mi_ecmp=PRO_US_NA_U_SITEBUNDLE_FULL_EN_10142026` uses plain HTTP. This is the QA "Image uses http://" warning, and clients that block mixed content will drop it.
- **Insecure content image:** `http://image.emails.skechers.com/lib/fe3115707564047a731c78/m/1/dde00662-169f-447d-b0e2-fc65f6c2290c.png` is also HTTP. If it is a visible image, it may not render. The same host should serve HTTPS.
- **Unverified links:** QA skipped 31 click-tracking links (HTTP probe skipped for tracking domains). Their destinations and status are unconfirmed.
- **Pixel stack:** the five pixels in the hidden `<div>` (SFMC open, three Krux/`beacon.krxd.net`, Return Path) plus the ink1000 pixel make six tracking requests. The Krux `width="0" height="0"` pixels have no `alt`.

## 3. Rendering & Accessibility
- **Missing alt (QA-confirmed):** `o.gif` (ink1000) and `dde00662-…png` have no `alt`. The Return Path pixel and the Krux beacons are also missing it, though QA did not flag them. If `dde00662-…png` is visible content, it needs descriptive alt text; the pixels need `alt=""`.
- **Meta tags:** `<meta content="text/html; charset=utf-8" />` and `<meta content="IE=Edge" />` have no `http-equiv`, so neither declaration takes effect. Charset then depends on the Content-Type header.
- **Zoom restriction:** the viewport meta sets `maximum-scale=1`, which blocks pinch-zoom where honored (WCAG 1.4.4).
- **Text scaling:** `* { -webkit-text-size-adjust: none }` disables text resizing on iOS.
- **Layout tables:** the visible tables (`<table class="widthFull" width="640" …>`) have no `role="presentation"`. Screen readers may announce them as data tables.
- **Hidden tracking markup:** the tracking tables use `display:none !important` and zero-size pixels. This is acceptable for hidden content, but it adds DOM weight.

## 4. Personalization & Merge Tokens
- **[FAIL, QA-confirmed] Empty greeting slot:** the greeting renders as `Hi ,`. The first-name field resolved to empty and no fallback was applied. The raw token wasn't in the truncated source, so I can't name the AMPscript variable. A default such as `%%=IIF(Empty(@firstName),"there",@firstName)=%%` would prevent this.
- No unrendered `%%…%%` or `{{…}}` tokens were visible in the portion available.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- **Not verifiable.** Raw headers (SPF, DKIM, DMARC, `List-Unsubscribe`, `List-Unsubscribe-Post`) were not provided. The footer was cut off, so the unsubscribe link and physical postal address were not checked.
- **Hashed identifier shared with a third party:** the Krux beacon `partner_uid=9153f33fe5cdf59baf088bb835d3b39ef90f188bd8540a4faba92899227ced00` is a 64-hex string, consistent with a SHA-256 of the recipient's email. The partner name is `…_sha25`. This is probably a hashed email and is sent to `beacon.krxd.net` on open without the recipient clicking anything. Whether the privacy policy covers this is worth confirming. I can't confirm the hash input from the source alone.
- The sender is `no-reply@emails.skechers.com`. A no-reply address is not a CAN-SPAM violation by itself, but it weakens reply-based opt-out paths.

## 6. Email-to-Site Continuity (UTM params, landing page alignment)
- **Not verifiable.** Click links were skipped by QA and the visible source is truncated, so UTM parameters and landing destinations can't be checked.
- The campaign identifier `PRO_US_NA_U_SITEBUNDLE_FULL_EN_10142026` appears in the Krux and ink1000 pixels. It could be compared against the UTM campaign values on the click links.

## 7. Recommendations
1. Add a fallback to the first-name merge field so the greeting never renders `Hi ,`.
2. Add `https://` to the Return Path pixel (`pixel.app.returnpath.net/pixel.gif`), or confirm that vendor's seed pixel is meant to be scheme-less.
3. Switch `ink1000.com` and `image.emails.skechers.com` to HTTPS. If ink1000 has no HTTPS endpoint, drop it.
4. Add `alt=""` to all tracking pixels and descriptive `alt` to `dde00662-…png` if it's visible.
5. Fix the meta tags: `<meta http-equiv="Content-Type" content="text/html; charset=utf-8">` and `<meta http-equiv="X-UA-Compatible" content="IE=edge">`.
6. Remove `maximum-scale=1` and `-webkit-text-size-adjust: none`, and add `role="presentation"` to layout tables.
7. Re-run the audit on the full HTML and raw headers. That would check the unsubscribe link, postal address, `List-Unsubscribe`, authentication results, and UTM consistency across the 31 skipped links.
8. Confirm that sending a hashed email to Krux on open is covered by the privacy disclosures.
