## 5. Recommendations

1. **Fix the cart page immediately.** A blank cart is a zero-revenue page. This is the single highest-priority fix on the site right now.

2. **Confirm login with visible feedback.** Show my name or a "Hi Walker" state somewhere in the header after login. If I can't tell I'm logged in, personalization is invisible and wasted.

3. **Add width selection to the size-selection step.** Before the ADD TO CART button, require width selection for any wide-fit eligible shoe. Don't make me hunt for it separately.

4. **Homepage hero should rotate to comfort messaging.** I don't need "GAME ON!" I need "Your feet deserve this." Even a secondary banner slot with Slip-ins + arch support imagery would help.

5. **Build out review volume on key products.** 7 reviews on an $88 ortho-comfort shoe is thin. I trust a shoe more when other people my age have confirmed it works. Prompt post-purchase review requests.

## Technical Audit

## Technical Summary

Eight-step mobile journey across skechers.com (Salesforce Commerce Cloud / Demandware). TTFB is consistently fast on cached pages (34–41ms) but doubles on category listing and cart (141ms). LCP and CLS are unsampled — the most diagnostic Core Web Vitals are absent. The site carries an unusually heavy third-party script payload in `<head>`, Kasada bot protection is actively rate-limiting the test session (including the cart page itself), and the View Cart page renders with a broken document structure (no `<title>`, no `lang`).

---

## Accessibility

**Critical (1)**
- `aria-required-parent` on Homepage: elements with ARIA roles that require a parent container (e.g., `role="option"` without `role="listbox"`) are orphaned. Screen reader behavior is undefined.

**Serious (2) — View Cart**
- `document-title`: `<title>` element is missing or empty. This is the cart page — assistive technology users get no page identity cue, and browser history/tab labels are blank.
- `html-has-lang`: `<html>` has no `lang` attribute on the cart page. Homepage correctly sets `lang="en"`. Likely a separate iframe or SPA shell for the cart that bypasses the standard template.

**Moderate (10)**
- Homepage has three overlapping landmark violations: `<main>` is not top-level, there are duplicate `<main>` elements, and `landmark-unique` fires — consistent with a page that renders both a server-side shell and a client-injected SPA fragment, each contributing its own `<main>`.
- `<aside>` (complementary) nested inside another landmark on Homepage and Search — violates ARIA landmark hierarchy.
- `heading-order` on Homepage: heading levels are skipped (likely `<h3>` without a preceding `<h2>`).
- Search results page repeats the complementary/landmark-unique violations, suggesting the same component tree as the category page.
- View Cart additionally lacks any `<main>` landmark and has no `<h1>`.

## SEO

- **View Cart missing `<title>`**: Even if the cart is `noindex`, a missing title breaks browser history, share previews, and internal link audits. It also indicates the cart page may be rendered in a separate document context (iframe or headless shell) that doesn't inherit the global template.
- **View Cart missing `lang`**: Same root cause as above. Googlebot and other crawlers use `lang` for language/region signals.
- No other SEO-critical issues observed in the sampled HTML. Homepage `<html lang="en">` is correct.

## Console & Network Errors

**429 Rate Limiting — Kasada KPSDK (5 hits)**

All 429s target:
```
/149e9513-01fa-4fb0-aad4-566afd725d1b/2d206a39-8ed7-437e-a3be-862e0f06eea3/fp?x-kpsdk-v=j-1.2.443
```

This is Kasada's bot fingerprinting endpoint. The GUID path segments are the tenant/session identifiers for the Kasada SDK (`x-kpsdk-v=j-1.2.443`). The endpoint polled repeatedly and received 429 on each attempt — meaning Kasada flagged the test session as bot traffic and blocked the fingerprint submission.

**Downstream consequence**: `/cart/` itself returned 429. When Kasada's fingerprint validation fails, it gates downstream requests. This is the mechanism — not a coincidence. In production, any legitimate mobile user whose browser fingerprint triggers Kasada's heuristics (VPN, older WebView, aggressive tracking prevention) would receive the same cart block.

**CORS block — Stylitics**
```
https://web-assets.stylitics.com/style.css?base=hotspots&theme=skechers&version=777c217f34
```
Blocked by CORS policy: missing `Access-Control-Allow-Origin`. The Stylitics CDN is not returning the required CORS header for stylesheet requests originating from `www.skechers.com`. The visual component this CSS drives (likely a shoppable hotspot widget) will render unstyled or broken.

**`net::ERR_FAILED`** (1): One resource failed at the network level before receiving an HTTP response — likely a blocked third-party tracker suppressed by the test environment's network layer.

## Recommendations

1. **Instrument LCP and CLS** on all 8 steps before any performance work. TTFB alone is insufficient. Use `web-vitals` or PerformanceObserver to capture real values — the current dataset has no actionable CWV data.

2. **Fix View Cart document structure**: The cart page renders with a separate document context that lacks `<title>` and `html[lang]`. Ensure the cart shell template includes these — or if the cart is an iframe, set `title` on the iframe element and add `lang` to the inner document.

3. **Fix the Stylitics CORS misconfiguration**: The CDN serving `web-assets.stylitics.com` needs `Access-Control-Allow-Origin: https://www.skechers.com` (or `*`) on stylesheet responses. This is a Stylitics-side config issue — raise with their support.

4. **Deduplicate third-party tags**: Remove the duplicate Yahoo pixel and audit which Monetate loader (`/js/2/` vs `/js/3/`) is canonical. Each redundant request adds RTT on mobile.

5. **Address the `aria-required-parent` critical violation**: Identify the component emitting orphaned ARIA role elements on Homepage (likely a carousel or autocomplete widget) and wrap them in the correct parent role container.

6. **Investigate Kasada false-positive rate on mobile**: The cart 429 downstream from fingerprint failure is a revenue-blocking path. Review Kasada's mobile WebView and tracking-prevention exception rules — legitimate iOS Safari users with "Prevent Cross-Site Tracking" enabled may be hitting this.

7. **Fix Homepage landmark duplication**: The dual-`<main>` pattern suggests the SFCC page shell and a client-side SPA fragment are both contributing structural landmarks. The server-rendered `<main>` should be the single source; client-injected content should not introduce a second one.
