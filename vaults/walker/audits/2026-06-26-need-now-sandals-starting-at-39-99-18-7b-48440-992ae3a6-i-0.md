### 3. Rendering & Accessibility

**`http-equiv` missing on two `<meta>` tags** — these attributes are silently dropped by some clients, making the declarations no-ops:
```html
<!-- as written — non-functional -->
<meta content="text/html; charset=utf-8" />
<meta content="IE=Edge" />

<!-- correct -->
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
```

**`Src:` capitalization in all `@font-face` blocks** — CSS property names must be lowercase. `Src:` is technically invalid; lenient parsers accept it but strict renderers (some webmail clients) will skip the entire font rule and fall back immediately:
```css
/* all 10 @font-face blocks use this — should be src: */
Src: url("https://braze-images.com/...") format('woff');
```

**Conflicting `text-size-adjust` values** — the global reset sets `-ms-text-size-adjust: 100%` and then immediately overrides with `text-size-adjust: none`. The `none` value suppresses all automatic text scaling on mobile, which is a WCAG 1.4.4 risk:
```css
*{
  -ms-text-size-adjust: 100%;   /* allow scaling on IE/Windows Phone */
  -webkit-text-size-adjust: 100%;
  text-size-adjust: none;        /* contradicts the above on all other clients */
}
```

**`maximum-scale=1` in viewport meta** — prevents pinch-to-zoom on mobile, flagged as an accessibility barrier (WCAG 1.4.4):
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```

**`font-weight: normal` on all font variants** — every `@font-face` including `Futura_PT_Bold` and `Futura_PT_Demi` declares `font-weight: normal`. Since they use distinct `font-family` names rather than a weight-stacked family, this is functionally harmless but semantically incorrect and will cause mismatches if any CSS ever references `font-weight: bold` within those families.
