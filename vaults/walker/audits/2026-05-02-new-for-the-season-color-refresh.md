### 3. Rendering & Accessibility

**Critical — Broken CSS values in `@media (max-width:480px)` block:**

```css
.nav_padding { padding-top:px !important; padding-bottom:px !important; }
.nav_border  { border-top:px solid ; }
```

Both rules have missing numeric values and (in `nav_border`) a missing color token. These will be silently ignored by all CSS parsers — any element using `.nav_padding` or `.nav_border` on mobile will receive no top/bottom padding and no border.

**Duplicate `<meta name="viewport">` tag:**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
<meta content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=yes" name="viewport" />
```

The two declarations contradict each other (`user-scalable=yes` vs. omitted). Browsers use last-declared; the second one wins, but the duplication is a build artifact suggesting template inconsistency.

**Missing `http-equiv` on charset meta:**

```html
<meta content="text/html; charset=utf-8" />
```

Should be `<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />`. Some older email clients (Lotus Notes, legacy Outlook) require the `http-equiv` attribute to correctly interpret charset — without it, character encoding may fall back to client default.

**Custom web fonts:** Four `@font-face` weights of `TheFutureHOKA` are declared, loaded from `hoka.com/on/demandware.static/…`. Web fonts are unsupported in Gmail (all clients), Outlook (all versions), and Yahoo Mail. Fallback font behavior cannot be verified from the truncated HTML — confirm that `font-family` declarations elsewhere specify a safe system-font fallback stack.

**Near-black/near-white anchor colors:**

```css
a { color: #000001; }
.footer_text a { color: #fffffe; }
```

Values are one step off pure black/white. This is a deliberate technique to suppress auto-detection link coloring in some clients. It is functional but worth flagging as intentional, not accidental — verify it is tracked as a known template decision.
