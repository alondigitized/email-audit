### 3. Rendering & Accessibility

**[HIGH] Duplicate, conflicting viewport meta tags**

```html
<!-- tag 1 -->
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
<!-- tag 2 -->
<meta content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=yes" name="viewport" />
```

Two `<meta name="viewport">` declarations are present. They conflict: tag 1 implicitly disables user zoom (no `user-scalable=yes`); tag 2 adds `user-scalable=yes`. Browsers use the last declaration, but behavior is undefined across email clients that parse the `<head>`. One declaration should be kept; `user-scalable=yes` is the accessible default.

**[HIGH] Malformed CSS — mobile padding and border rules produce no output**

```css
/* @media (max-width:480px) */
.nav_padding { padding-top:px !important; padding-bottom:px !important; }
.nav_border  { border-top:px solid ; }
```

Both rules are missing the numeric value before `px` and `.nav_border` is also missing the color value. These declarations are invalid and will be discarded by every CSS parser. If `.nav_padding` or `.nav_border` are applied to mobile nav elements, those elements will inherit no padding/border override, causing layout collapse or overflow on small screens.

**[MEDIUM] Charset meta missing `http-equiv` attribute**

```html
<meta content="text/html; charset=utf-8" />
```

Should be:
```html
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
```

Without `http-equiv`, the charset declaration is not valid per RFC 2557 / HTML email conventions. Outlook desktop parses this header to determine encoding; omitting it risks mojibake on accented characters.

**[LOW] Custom web fonts — no email-client fallback chain visible in excerpt**

`TheFutureHOKA` and `TheFutureHOKAMono` are declared via `@font-face`. Gmail (web and app), Outlook 2007–2021, and Samsung Mail do not render `@font-face` fonts. The audit cannot confirm fallback `font-family` stacks without seeing the full inline styles on text elements; if fallbacks are absent, those clients will render in the browser default serif.

**[LOW] Near-black / near-white anchor colors**

```css
a { color: #000001; }
.footer_text a { color: #fffffe; }
```

Off-by-one from true black/white (`#000000` / `#ffffff`). This is a known spam-filter evasion pattern some ESPs use deliberately — confirm it is intentional, as it has no rendering impact but may flag rule-based content scanners.
