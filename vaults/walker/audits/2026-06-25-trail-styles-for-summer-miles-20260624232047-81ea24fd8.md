### 3. Rendering & Accessibility

**Duplicate `<meta name="viewport">` (confirmed bug)**
Two viewport declarations appear back-to-back with conflicting values:
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
<meta content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=yes" name="viewport" />
```
The second overrides the first. The first disallows user scaling (`maximum-scale=1`, no `user-scalable`); the second re-enables it (`user-scalable=yes`). Browser/client behavior on duplicate viewports is inconsistent. Remove the first and keep the second (accessibility best practice requires `user-scalable=yes`).

**Empty `<title>` tag (confirmed bug)**
```html
<title></title>
```
Blank title renders as an empty tab label in webview and breaks some preview-text implementations in clients that read `<title>` as fallback subject line.

**Malformed CSS — `.nav_padding` (confirmed bug)**
```css
.nav_padding {padding-top:px !important; padding-bottom:px !important;}
```
Missing numeric values before `px`. These declarations are invalid and will be silently dropped by all parsers. If this class controls mobile nav spacing, that spacing is zero on ≤480px viewports.

**Malformed CSS — `.nav_border` (confirmed bug)**
```css
.nav_border {border-top:px solid ;}
```
Missing width value and missing color value. Rule is invalid; border will not render.

**`@font-face` without system fallback (risk)**
Five `@font-face` blocks load `TheFutureHOKA` and `TheFutureHOKAMono` from `hoka.com`. Gmail (web and Android) strips `@font-face` entirely. The truncated source does not show the `font-family` stack used on body text. If fallback is missing or set only to `TheFutureHOKA`, Gmail renders in Times New Roman by default. Verify that inline `font-family` values on `<td>` and `<p>` elements include a web-safe fallback (e.g., `"TheFutureHOKA", Arial, sans-serif`).

**`* { border: none; }` universal reset (low risk)**
The global `*` reset zeroes margin, padding, and removes borders on all elements. This can strip focus outlines from interactive elements in webview rendering, which is an accessibility concern if the email renders in a browser context.
