## Technical Audit

**1. Technical Summary**
The email's HTML structure is sound (XHTML Transitional, MSO conditionals, preheader hack), but the QA run found a missing plain-text part, 4 product links that returned 403, and 4 images without alt text. A mojibake bug in the preheader and missing header data (List-Unsubscribe, Authentication-Results) limit what can be confirmed about compliance and authentication.

**2. Link & Tracking Issues**
- **4 "SHOP NOW" links returned HTTP 403** (QA `[FAIL]`):
  - `/disney-villains-maleficent-dragon-plush/032609.html`
  - `/sanrio-spooky-webs-cinnamoroll-plush/035164.html`
  - `/sanrio-starry-sky-hello-kitty-plush/035171.html`
  - `/fresno-nightcrawler-posable-plush/034979.html`
- All four are on `www.buildabear.com`. A 403 on a normal product URL is most likely bot-blocking of the QA probe (WAF or Salesforce Commerce Cloud) and not a dead page. It is not confirmed as a broken link. A real browser check is needed before treating these as outages.
- The link text for all four is "SHOP NOW", so the check can't tell the products apart. Each product also appears to have a separate `<a>` for its image and for its CTA, though the truncated source doesn't show this.
- 26 tracking links were skipped by the HTTP probe because they are click-redirect domains. Their destinations are unverified.

**3. Rendering & Accessibility**
- **Preheader encoding bug**: the source contains `Itâ€™s the Grinch!`. This is UTF-8 right-single-quote bytes decoded as Windows-1252, so the apostrophe is mangled. The `<meta charset=utf-8>` is correct, so the corruption happened upstream in the template or ESP. Inbox clients will show the garbled text as preview text next to the subject.
- **A stray `</span>`** sits right after the preheader `<div>`, with no matching opening tag in the visible source. This is invalid markup and could trigger quirks in some clients.
- **4 images have no alt text** (QA `[WARN]`):
  - `88240802332609~x20101015.jpg`
  - `32250800435164~x20117123.jpg`
  - `98250800435171~x20127120.jpg`
  - `08250701634979~x20230105.jpg`

  These are the product images served from `dw/image/v2/BBNG_PRD/...`. If they are wrapped in links, screen readers and image-blocked clients will have no accessible name for the link.
- **Plain-text part is missing**: `[FAIL] Text version is 0 chars`. This is a multipart/alternative gap that hurts accessibility and spam scoring.
- `<meta name="color-scheme" content="light dark">` is declared. The visible CSS has no `prefers-color-scheme` rules, so dark-mode rendering is left to client auto-inversion.
- Responsive breakpoints are defined (`max-width:480px`, `481–639px`), and `<title>` is a template name ("Build-A-Bear_BroadcastTemplate_1A"), not a descriptive title. That is minor.

**4. Personalization & Merge Tokens**
No issues found. No unrendered merge tokens (`%%…%%`, `{{…}}`, `[[…]]`) appear in the visible source. The source is truncated, so the footer isn't covered.

**5. Compliance (CAN-SPAM, unsubscribe, authentication headers)**
- `[WARN]` List-Unsubscribe not found, and `[WARN]` List-Unsubscribe-Post (RFC 8058) not found. The QA notes say the AgentMail relay may strip these headers. **This can't be confirmed as a sender defect.** Gmail and Yahoo bulk-sender rules require both headers, so verify them against the raw message at the source.
- `[WARN]` Authentication-Results not found. SPF, DKIM and DMARC status is unknown, and the same relay caveat applies. The From domain is `ebuildabear.com`, so check alignment of the envelope and DKIM domains with it.
- The physical address and visible unsubscribe link are in the truncated footer, so they can't be evaluated here.
- The missing plain-text part (section 3) is also a deliverability issue.

**6. Email-to-Site Continuity (UTM params, landing page alignment)**
- All four product links share the same UTM set: `utm_source=Campaign`, `utm_medium=Email`, `utm_campaign=NEWGrinchLaunch`, `utm_content=Promo`, `utm_id=2801042`, plus a long `utm_term`. Tagging is consistent.
- **Content mismatch**: the subject and preheader are about the Grinch, but the four checked destinations are Maleficent, Cinnamoroll, Hello Kitty and Nightcrawler products, none of them Grinch/Seuss items. The campaign name `NEWGrinchLaunch` and `utm_term` (`..._Seuss_Omni_...`) both indicate a Grinch launch. I can't tell whether Grinch products appear in other, unchecked links, or whether these four were wrongly substituted by dynamic content. Verify this.
- **`utm_content=Promo` is identical on all four links**, so link-level click attribution can't separate them. `utm_content` could carry a per-slot identifier.
- **`utm_term` is overloaded**: it holds a 100+ character internal string with a timestamp (`1792162274030`), segment (`US-UNION`) and campaign metadata. This is not a keyword, and it makes reporting messy.
- **`utm_source=Campaign`** is a generic value and doesn't identify the ESP or list.

**7. Recommendations**
1. Re-test the four 403 product URLs in a real browser or with a browser-like user agent. If the pages load, mark these as probe false positives. If not, fix them before further sends.
2. Verify that the Maleficent, Cinnamoroll, Hello Kitty and Nightcrawler products belong in a Grinch-themed send.
3. Fix the UTF-8 / Windows-1252 mismatch behind `Itâ€™s` in the preheader, and remove the stray `</span>`.
4. Add descriptive `alt` text to the four product images, including the `08250701634979~x20230105.jpg` one, and set `<title>` to something descriptive.
5. Add a plain-text MIME part. A 0-character text version is a hard fail.
6. Check the raw message for `List-Unsubscribe`, `List-Unsubscribe-Post` and `Authentication-Results`. If they are missing there too, add them.
7. Give each link its own `utm_content`, and move the internal metadata out of `utm_term` into `utm_id` or a custom parameter.
