## Technical Audit

## 1. Technical Summary
The email is structurally sound: table layout, responsive media queries and consistent UTM tagging. Its main defects are a missing plain-text part, four product images with no alt text, and four product links that returned HTTP 403 in the QA probe. The header-based compliance checks couldn't be verified.

## 2. Link & Tracking Issues
- **Four "SHOP NOW" links returned 403.** All four go directly to buildabear.com PDPs:
  - `/smiley-monkey-stuffed-animal-skeleton-gift-set/25539_27647_24630.html`
  - `/pawlette-bunny-plush-halloween-cardigan-gift-set-with-jack-o-lantern-bucket/33639_35019_35120_35020_22920.html`
  - `/happy-hugs-teddy-bear-pumpkin-dress-gift-set/25567_35065_35120_22920.html`
  - `/pawlette-bunny-plush-black-school-uniform-gift-set/33639_35063_35120_34410.html`
- **The 403s are probably bot blocking, not dead pages.** The domain is Salesforce Commerce Cloud (`/dw/image/v2/BBNG_PRD/...`), and a 403 on an automated request is the usual WAF response there. It needs a manual check with a browser user-agent before calling these broken. If the pages really are unavailable, all four product CTAs are dead.
- **The QA output shows an empty link-text field** (`link text: ""` before the quoted "SHOP NOW"). The link text is captured inconsistently, which suggests the anchors wrap images or nested markup.
- **23 tracking/redirect links were skipped** and not probed. Those are likely the nav, footer and unsubscribe links, so their destinations are unverified.

## 3. Rendering & Accessibility
- **Four product images have no `alt` attribute.** The filenames are `…25539_27647_24630x20555013.jpg`, `…33639_35019_35120_35020_22920~x20547071.j…`, `…25567_35065_35120_22920~x20822077.jpg` and `…33639_35063_35120_21512~x20534070.jpg`. With images blocked, these render as empty boxes. Screen readers will read the URLs or skip the images.
- **The image `src` filename shows `…35063_35120_21512…`** while the linked PDP ID is `…35063_35120_34410`. The trailing SKU segment differs, so the pictured variant may not match the linked product. Confirm this against the live pages.
- **There is a stray `</span>`** before `<!-- AMP -->` with no matching opening tag. Most clients tolerate it, but it is invalid markup.
- **`<meta name="color-scheme">` and `<meta name="supported-color-schemes">` are not self-closed** under an XHTML 1.0 Transitional doctype. This is minor and harmless in practice.
- **`<title>` contains the internal template name** `Build-A-Bear_BroadcastTemplate_1A`. It is visible in some webmail tabs and "view in browser" pages.
- **The preheader is duplicated.** There is a `div.preheader` with the text and a second hidden div padded with `&zwnj;&nbsp;&shy;` characters. The padding is the standard technique and is fine. The `&shy;` run is very long, though, and the source is truncated, so its total size can't be judged.
- **No issues found** with viewport, `mso` conditionals or the responsive breakpoints (481–639px, ≤480px, ≤350px).

## 4. Personalization & Merge Tokens
No issues found. The visible HTML has no unrendered merge tokens (`%%…%%`, `{{…}}`, `[[…]]`). The campaign name contains "Dynamic", and `utm_term` carries a per-send/recipient ID (`US-UNION_1790090141347_092926…`). The source is truncated, so any greeting or body tokens further down can't be confirmed.

## 5. Compliance
- **[FAIL] The plain-text alternative is 0 characters.** The QA check found no text/plain part. This is a deliverability and accessibility risk, because some filters penalise HTML-only mail.
- **[WARN] `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058) were not found.** The QA note says AgentMail may strip them, so this is unconfirmed. Gmail and Yahoo require one-click unsubscribe for bulk senders. Check the raw headers at the source.
- **[WARN] `Authentication-Results` was not found,** so SPF, DKIM and DMARC alignment are unknown. The sender is `buildabear@ebuildabear.com`, a subdomain of the brand domain. That is standard, but the relay hides the evidence.
- **The footer unsubscribe link and physical postal address can't be checked.** They fall in the truncated portion of the source, and the 23 tracking links weren't probed.

## 6. Email-to-Site Continuity
- **UTM tagging is consistent across all four product links:** `utm_source=Campaign`, `utm_medium=Email`, `utm_campaign=HalloweenSpookyStuffDynamic`, `utm_content=Promo`, `utm_id=2796666`.
- **`utm_content=Promo` is identical on every link.** Clicks can't be attributed to a specific product or placement in analytics. Per-slot values such as `promo_1` to `promo_4` would fix that.
- **`utm_source=Campaign` is a generic value,** not a channel or platform name. It may blend with other sources in reporting.
- **`utm_term` is very long,** and it holds a recipient/send ID, a date and a campaign taxonomy string. This overloads the field and lengthens every URL. Only `utm_id` (2796666) is a clean, stable join key.
- **Landing-page alignment couldn't be verified,** because all four destinations returned 403 to the probe. The links do point to gift-set PDPs, which fits a product-focused email.

## 7. Recommendations
1. Re-test the four PDP URLs with a browser user-agent or from a residential IP. If they return 200, treat the 403s as probe false positives and allow-list the QA crawler.
2. Add descriptive `alt` text to the four product images, for example the product name plus "gift set". Also check that each image's SKU segment matches its linked PDP.
3. Add a text/plain part to the multipart message.
4. Verify `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` on the raw message, and check SPF, DKIM and DMARC pass outside the relay.
5. Make `utm_content` unique per link, and move the recipient/send ID out of `utm_term`.
6. Remove the stray `</span>`, and replace the `<title>` with a customer-facing string.
7. Re-run the audit on the full, untruncated HTML to check the footer (unsubscribe link, postal address) and any remaining tokens.
