# Hot blooms for summer birthdays
**Score:** 7/10 · **Type:** Email audit · **2026-06-23**
## Executive summary

- This is a listicle send — "The 5 Hottest Birthday Blooms" — arriving on June 23, one day after 1-800-Flowers ran "What We're Sending for Summer Birthdays (+ $13.80 Credit)" to essentially the same audience with the same birthday/summer angle. The one-day gap matters: to a real subscriber, these two hits bleed together and the second one feels redundant before it's even opened. The editorial numbered format is a competent break from the Double Blooms clone cycle, but the differentiation is format, not offer — there's nothing concrete tying this to a reason to buy today.
- That said, the render is clean. Free shipping is called out in the banner, the five products are legible, and the numbered scroll structure gives a mobile reader a reason to keep going. It's functional, not lazy. But it's also the second birthday email in 24 hours, and it offers weaker financial incentive than yesterday's $13.80 credit framing — which makes the cadence problem worse, not better.
- Bottom line: a well-designed listicle that would score higher if it arrived in isolation, but lands diminished because of what came before it.

## What's working

- Numbered editorial format is genuinely scannable — five products with distinct names and images reward a quick scroll.
- "Free Shipping & Service Charge" banner is front-loaded at the top, visible before the fold.
- "The 5 Hottest Birthday Blooms" headline is clear, seasonal, and occasion-specific with no ambiguity about what's being sold.
- Celebrations Passport placement near the bottom is a natural loyalty upsell for a returning buyer.
- Clean render — no broken images, no layout overflow, no visual junk.

## What's weak

- Arrives 24 hours after an essentially identical birthday send (June 22) at a weaker offer — the $13.80 credit yesterday was more concrete than free shipping today.
- "SHOP TRENDING" is a generic CTA verb — no specific pull toward any of the five products.
- Five co-equal hero products fragment attention; there's no single breakout product with price, social proof, or urgency to anchor a click.
- No time-bound urgency in subject or body — "hot" is a style word, not a deadline.
- Product prices (if visible at all at this image resolution) aren't hero-level — the financial hook is buried below the fold.

## Recommendations

- 1. **Collapse the cadence** — one birthday email every 3–4 days, not back-to-back. This send would have landed cleaner on June 25 or 26.
- 2. **Pick a single hero product and anchor it with price** — "No. 1: Vibrant Memories Bouquet — $X, free shipping today" is more clickable than five equal options.
- 3. **Sharpen the CTA copy** — "Shop Birthday Blooms" or "See All 5" beats "Shop Trending."
- 4. **Add a light urgency layer** — even "ships in time for the weekend" or "order by Thursday" beats nothing.
- 5. **Restore the credit mechanic from June 22** — the $13.80 credit framing in yesterday's email was more motivating; using a real dollar figure here instead of just free shipping would differentiate this send instead of weakening it.

### 3. Rendering & Accessibility

**Issue 1 — Aggressive universal reset breaks line-height inheritance**
```css
* { line-height: 100%; }
```
Applying `line-height:100%` to every element overrides browser defaults on all descendants including `<p>`, `<td>`, and font fallback stacks. This can compress multi-line text in clients that don't support `!important` overrides (e.g., Gmail web, Samsung Mail). The accepted pattern is to scope this to `body` and `table td` only.

**Issue 2 — Redundant, overlapping image max-width media queries**
```css
@media only screen and (min-width: 768px) { img { max-width:640px } }
@media only screen and (min-width: 640px) { img { max-width:640px } }
```
The 768px rule is fully subsumed by the 640px rule — both resolve to the same value. The 768px block is dead code. One of them should be removed.

**Issue 3 — Hardcoded 414px mobile widths instead of fluid**
```css
.mobile  { width:414px !important; }
.showmobile { width:414px !important; }
```
Both classes hardcode iPhone 6/7/8 logical pixels. Any device with a viewport between 414–418px but a different DPR, or a non-iPhone device at that breakpoint, gets a fixed-width container rather than `100%`. Use `width:100% !important` and constrain via the parent container.

**Issue 4 — Mobile breakpoint gap**
The responsive trigger fires at `max-width: 418px` but mobile widths are set to `414px`. The 4px gap exists to avoid the breakpoint clipping on 414px devices, but the magic number is fragile — use `max-width: 480px` or `600px` per standard practice to cover Android/tablet portrait modes.

**Issue 5 — Global `th` font-size override**
```css
th { font-size:20px !important; }
```
Declared globally in `<style type="text/css">` — any `<th>` in nav or structured data tables (e.g., price tables) inherits this value unconditionally. Should be scoped to a named class.

**Issue 6 — Inconsistent font versions for Playfair Display**
```
v21 — weight 400 italic, weight 400 normal, weight 600 normal
v22 — weight 900 italic, weight 900 normal
```
Mixing v21 and v22 of the same family from `fonts.gstatic.com` risks metric discrepancies between weights, causing layout shifts on clients that render web fonts. Pin to a single version.

**Issue 7 — Playfair Display weight-900 normal loads `.woff`, not `.woff2`**
```css
src:url(https://fonts.gstatic.com/s/playfairdisplay/v22/...btM.woff) format('woff');
```
All other Playfair and Lato declarations load `.woff2`. `.woff` is ~30% larger and not required — a `.woff2` equivalent for this weight/style exists. This is a bandwidth regression on clients that do render external fonts.

**Issue 8 — `mso-font-alt` missing from several @font-face blocks**
Only two Playfair Display `@font-face` declarations include `mso-font-alt:'Times New Roman'`. The remaining four Playfair weights and all six Lato weights are missing it. Outlook desktop will use its default fallback (typically Calibri) rather than the declared fallback, causing visual inconsistency.
