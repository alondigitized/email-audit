# Which bouquet feels most like them?
**Score:** 6/10 · **Type:** Email audit · **2026-10-29**
## Executive summary

- This is a "This or That" send that repeats the 10/23 "Pick Your Favorite Bouquet" concept almost exactly. It has the same green-striped hero, the same "Playing Favorites" script and the same head-to-head matchups. The change is the offer: 25% off with code GLOW25, where the 10/26 Halloween send used 20% off with GLOW20. The layout is clean and the photography is strong. The three versus pairs (Moody vs. Neutral, Farmhouse vs. Penthouse, Spooky vs. Scary) are easy to scan.
- The subject, "Which bouquet feels most like them?", is a gifting-emotion hook. The body never pays it off. Nothing explains how to choose for a specific person, and the discount sits in a thin banner at the top. The subscriber has now had a "double" send on 10/27 and 10/28, and this is the third "favorites"-style send in a week. It reads as a template rerun, not a new reason to act.
- Verdict: competent and polished, but a repeat. The core problem is that the matchups ask you to pick a favorite, and no pick leads to a specific product or a decision.

## What's working

- The 25% off code GLOW25 is the first thing in the hero strip, so the offer is visible immediately.
- The three versus pairs are visually balanced, and the yellow "VS" circles make the mechanic obvious.
- The fall and Halloween palette (burnt orange, burgundy, green roses) fits the season.
- The hero has one clear orange "Shop Now" button.
- The category grid near the bottom (Birthday, Sympathy, Same-Day, and others) gives browsers a way in.

## What's weak

- The checkbox glyphs under each bouquet look like a poll, but they appear non-functional. Each pair also gets a single shared button, so there is no way to "vote" for one side.
- The same orange button appears four times ("Shop Now", "Shop Fall", "Shop Fall", "Shop Halloween"). The copy is generic, and the first two pairs both go to "Shop Fall", which dilutes the choice.
- The offer terms and expiry are in tiny footer text, so the urgency is never visible in the body.
- The NYC Marathon "Give Them Their Flowers" tote block is an off-theme interruption between the pairs and the category grid. It competes with the main story.
- The subject promises a "them" angle (recipient personality), but the body only compares bouquet styles and never mentions a person.

## Recommendations

- 1. Make each pair a real choice: separate "Shop Autumn Fields" and "Shop Graceful Fall" buttons, with the price visible under each bouquet. This would lift the email most.
- 2. Put the code and a deadline in a visible banner, for example "25% off ends tonight, code GLOW25", instead of leaving the date in the fine print.
- 3. Cut the tote block, or move it below the category grid, so the matchup story runs uninterrupted.
- 4. Differentiate this from the 10/23 send. Frame the pairs around the recipient ("For the cozy one" vs. "For the dramatic one") so the subject's promise is kept.
- 5. Drop the checkbox glyphs unless they work.
- **Subject Alt A:** `Moody or sweet? Pick the bouquet that fits them`
- **Subject Alt B:** `25% off bouquets for every personality`
- **Preheader Alt A:** `Three matchups, one code: GLOW25 takes 25% off. Ends tonight.`
- **Preheader Alt B:** `Autumn Fields or Graceful Fall? Find the one that sounds like them.`

## Technical Audit

## 1. Technical Summary
The email uses standard XHTML table-based markup with dark-mode meta tags and a mobile media query. The QA data shows no hard failures (0 issues, 5 warnings). The main concerns are that the compliance headers and physical address could not be confirmed, and that several tracking pixels are insecure or lack alt text. The HTML source was truncated, so the body, footer and link `href`s were not available to check.

## 2. Link & Tracking Issues
- **Unprobed links:** 33 tracking links were skipped because they are click-redirect domains, so none were verified to resolve. That is a QA coverage gap, not a confirmed defect.
- **Insecure pixels (`http://`):** these may be blocked or trigger mixed-content handling in some clients.
  - `http://view.atdmt.com/FLO/view/361227669/direct/01/`
  - `http://pixel.mathtag.com/event/img?mt_id=155437&mt_adid=103507&v1=&v2=&v3=&s1=&s2=&s3=`
  - `http://pixel.mathtag.com/event/img?mt_id=155438&mt_adid=103507&...`
- **Empty parameters:** the MediaMath pixel URLs carry empty `v1`–`v3` and `s1`–`s3` values, so the template variables appear unpopulated. This is probably harmless but suggests the pixel is not passing data.
- **Duplicate beacon:** `https://bounceexchange.com/tag/em/1622.gif` appears twice, which can double-count events.
- **Third-party pixel load:** four or more third-party beacon domains are loaded (atdmt, mathtag, bounceexchange, `click.dv.1800flowers.com`). This adds weight and privacy exposure, and any of them can be blocked by Apple Mail Privacy Protection or image blocking.

## 3. Rendering & Accessibility
- **Missing alt text:** QA flagged 6 images, all of them tracking pixels or beacons.
  - `view.atdmt.com/...`
  - both `mathtag` pixels
  - `bounceexchange.com/tag/em/1622.gif` (twice)
  - `click.dv.1800flowers.com/o/fd2651e1-...`
  - `mi.1800flowers.com/p/up/.../o.gif`
  
  Tracking pixels should carry `alt=""` plus `width="1" height="1"` so screen readers skip them. The alt text on content images was not checked in the truncated source.
- **Zoom blocked:** `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />` stops pinch-zoom on some mobile clients, which is a WCAG 1.4.4 concern.
- **Dark mode:** `color-scheme: light dark` is declared, but the `th` rule forces `color:#000000 !important` (also on `th a`). In dark mode this can leave black text on a dark background if the cell backgrounds are inverted. This is only a risk, since the full markup was not available.
- **Mobile layout:** `.mobile`, `.showmobile` and `.hide` use `!important` overrides with fixed `414px` widths under an `@media (max-width: 418px)` breakpoint. Clients that strip `<style>` blocks (some Gmail account types) would lose the responsive behavior.

## 4. Personalization & Merge Tokens
No issues found. No unresolved merge tokens (`{{ }}`, `%%`, `[[ ]]`) were visible in the truncated source.

## 5. Compliance (CAN-SPAM, unsubscribe, authentication headers)
- **Physical address (WARN):** none was detected. It may sit in the truncated footer, so verify it.
- **`List-Unsubscribe` and `List-Unsubscribe-Post` (WARN):** neither header was found. QA notes the AgentMail relay may strip them, so this is unconfirmed. If the sender omits them, the email lacks RFC 8058 one-click unsubscribe, which Gmail and Yahoo require of bulk senders.
- **`Authentication-Results` (WARN):** the header is missing, so SPF, DKIM and DMARC status could not be assessed. The `From` domain is `em.1800flowers.com`, a dedicated sending subdomain, but alignment is unverified.
- **In-body unsubscribe link:** not confirmed, because the footer was outside the truncated source.

## 6. Email-to-Site Continuity (UTM params, landing page alignment)
Not assessable. No `href`s or UTM parameters were visible in the truncated source, and the 33 tracking links were not probed, so landing-page alignment is unverified. One partial signal: the `mi.1800flowers.com` pixel URL contains `mi_ecmp=261029_EMAIL_18F_PZ_DV_12AMET_PROMO`, which suggests campaign tagging is present on the Movable Ink side.

## 7. Recommendations
1. Re-run QA against the full HTML to inspect the footer, the unsubscribe link, the physical address and the link `href`s.
2. Capture the raw headers from the original delivery, not the relay copy, to confirm `List-Unsubscribe`, `List-Unsubscribe-Post` and the SPF/DKIM/DMARC results.
3. Move the `atdmt` and `mathtag` pixels to HTTPS, or remove them if they are legacy.
4. Add `alt=""` and explicit 1×1 dimensions to all tracking pixels, and drop the duplicate `1622.gif` beacon.
5. Remove `maximum-scale=1` from the viewport meta tag.
6. Test dark-mode rendering of the `th` `#000000 !important` color rule.
7. Probe a sample of the 33 tracked links to check for redirect chains and UTM preservation at the landing page.
8. Check that the MediaMath pixel variables (`v1`–`v3`, `s1`–`s3`) are being populated.
