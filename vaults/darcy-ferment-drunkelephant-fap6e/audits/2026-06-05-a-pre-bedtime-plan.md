### 3. Rendering & Accessibility

**Critical: HTML comment syntax inside `<style>` block**

Lines in the `@media only screen and (max-width: 600px)` block use HTML comment delimiters inside CSS:

```css
@media only screen and (max-width: 600px) {
  *[class=hide] { display: none !important;}
  <!-- *[class=contenttable] { width:414px !important;} -->
  <!-- *[class=mobile] { width:414px !important;height: auto !important;} -->
```

`<!-- -->` is not valid CSS syntax. Inside a `<style>` block, this is a parsing error. Some email clients (notably older Outlook WebApp, Yahoo) will either skip the entire block or treat the comment delimiters as part of a selector, breaking the surrounding rules. The commented-out `contenttable` and `mobile` responsive overrides will never apply, likely degrading mobile layout.

**Triple font loading — redundant requests**

For BrownBold, BrownLight, and BrownThin, the same font is declared three times:
1. `<link href="https://db.onlinewebfonts.com/c/...">` in `<head>`
2. `@import url(https://db.onlinewebfonts.com/c/...)` in `<style>`
3. `@font-face { src: url("https://db.onlinewebfonts.com/t/...") }` in `<style>`

This triggers up to 3× the HTTP requests per font variant on clients that parse all three. BrownRegular is served correctly from `drunkelephant.com/on/demandware.static/...` with no duplication — the other variants should match this pattern.

**Invalid fragment identifier in SVG font reference**

```css
url("https://db.onlinewebfonts.com/t/4150d76a852e1c349e0b6fe15f29d9ca.svg#Brown Bold")
```

The fragment `#Brown Bold` contains an unencoded space. Per RFC 3986, this must be `#Brown%20Bold` or the reference will fail to resolve in SVG-aware parsers. SVG fonts are only relevant to very old iOS Safari (pre-2013), but the invalid URL may trigger parser warnings in strict clients.

**`*{line-height: 100%}` global reset**

This universal rule overrides line-height on all elements, including those where the inherited value would produce better readability. Confirm that all text containers have explicit `line-height` values set, otherwise this rule will produce tight text in Gmail.
