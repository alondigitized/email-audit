### 3. Rendering & Accessibility

**3a. Unresolved template placeholder shipped to production**
```html
<!--[IMPUT HERE CLIENT FONT IMPORT SCRIPT if needed]-->
```
This is a build-time instruction comment (with a typo: "IMPUT" vs "INPUT") left verbatim in the sent email. No custom font was injected. Consequence: intended web fonts are absent; system font fallbacks are rendering instead.

**3b. Conflicting `img max-width` media queries**
```css
@media only screen and (min-width: 768px) { img { max-width: 600px } }
@media only screen and (min-width: 640px) { img { max-width: 640px } }
```
Both target desktop breakpoints. At viewports ≥768px, cascade order gives priority to the `640px` rule (it appears last in the stylesheet), so images render at 640px rather than the intended 600px cap. The 768px rule is effectively dead code. Either collapse to one rule or reorder them.

**3c. `maximum-scale=1` in viewport meta**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
```
Prevents iOS users from pinching to zoom. This is a WCAG 1.4.4 (Resize Text) violation and was flagged by Apple as an accessibility regression. Remove `maximum-scale=1`.

**3d. Global `-webkit-text-size-adjust:none` overrides body-level `100%`**
```css
/* body rule (set first): */
body { -webkit-text-size-adjust: 100%; }

/* * rule (set later, wins): */
* { -webkit-text-size-adjust: none; }
```
The wildcard rule silently nullifies the body rule. On older WebKit clients this disables automatic text scaling entirely. Change the `*` rule to `none` → `100%` or remove the body rule in favor of the `*` rule set to `100%` — not `none`.

**3e. Hardcoded `.showmobile` width**
```css
.showmobile { width: 414px !important; }
```
Hardcoded to iPhone 12/Pro width. On narrower Android devices (~360px) this forces horizontal scroll. Use `width: 100% !important` instead.

**3f. No dark mode support**
```html
<meta name="color-scheme" content="light">
<meta name="supported-color-schemes" content="light">
```
Only `light` is declared. Apple Mail and Gmail on iOS will still force dark-mode color inversions on images and background colors, but no `prefers-color-scheme: dark` CSS overrides exist to control the output. Low severity but worth addressing for Apple Mail users.

**3g. Internal production comments visible in rendered source**
```html
<!-- /* General settings start */ -->
<!----- MI styling end----->
<!----- CLIENT styling start----->
<!--V2-->
```
None of these affect rendering, but they expose ESP/vendor internal tooling labels to anyone who views source.
