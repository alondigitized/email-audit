# Sale: now up to 70% off
**Score:** 5/10 · **Type:** Email audit · **2026-06-29**
## Executive summary

- This is ASOS's seventh summer sale email in eight days — and the offer has now escalated to 70% off, up from 60% on June 22. The headline does its job ("SALE: NOW UP TO 70% OFF") in bold red-on-black, but the creative is functionally identical to every send before it: nav marquee, hero headline, shop-all CTA, quick-filter buttons, a product editorial grid, brand logos, app download. There's no new hook — no code, no deadline, no "final hours" urgency that would give a fatigued subscriber a reason to act *today* rather than hitting archive.
- The escalation mechanic is losing steam. June 24's "extra 10% off" had a code and a Monday cutoff — that's a reason to click now. This one just says "up to 70% off" with no time fence. A subscriber who's already been through six rounds of "sale starts / extra 10% / new brands / 25% more off" will treat this as noise unless you give them a ticking clock.
- Structurally the email is clean and renders without visible bugs. The product imagery is strong, the quick-filter row (Under £10 / Under £30 / Bestsellers) is a genuine usability win, and the editorial grid is well-shot. But the cadence at this point is working against the offer — this is the fifth or sixth inbox hit, and the creative differentiation is essentially zero.

## What's working

- **Offer escalation is visible and clear** — "70% off" is the highest number in the sequence; the headline captures it immediately.
- **Quick-filter row is useful** — Under £10, Under £30, Bestsellers give hesitant shoppers a low-friction entry point that most sale emails skip.
- **Product grid is editorially varied** — dress, jacket/shorts set, sandals — covers multiple categories without feeling random.
- **No render bugs** — layout, images, and text all appear intact at this render size.
- **"Selling Fast" module** is a smart social-proof nudge placed mid-scroll, before the user loses momentum.

## What's weak

- **No deadline or urgency signal** — the June 24 escalation had a code expiring Monday; this one has nothing. "Up to 70% off" with no end date reads as permanent, which kills urgency.
- **Marquee is repetitive noise** — "FURTHER REDUCTIONS FURTHER REDUCTIONS" on loop adds visual clutter but zero information a subscriber doesn't already know from the headline.
- **Creative is indistinguishable from prior sends** — same layout, same image style, same CTA copy as June 22, 24, 25, and 28. A subscriber who's seen all of them gets nothing new.
- **Hero subtext is unreadable at mobile width** — the small grey copy beneath the headline appears truncated/illegible in the render, wasting the one sentence of supporting context.
- **App download block feels out of place** — slotted between brand logos and the footer, it interrupts the shopping flow and isn't relevant to someone already engaged with the sale.

## Recommendations

- 1. **Add a hard deadline** — "Ends midnight Sunday" or a countdown-style copy block is the single highest-lift change. The June 24 send scored 9/10 precisely because it had a code + a cutoff. Without a clock, a 70% off headline doesn't outperform a 60% off headline.
- 2. **Lead with the escalation story** — "We went from 60% to 70% — this is the deepest it gets" is a better frame than a flat headline restat. Makes the subscriber feel the trajectory.
- 3. **Replace the marquee with a category teaser** — e.g., "Shoes from £8 · Dresses from £6 · Swimwear from £5" gives concrete anchors and earns the scroll instead of adding visual noise.
- 4. **Kill the app download block** — it's friction inside a sale email. Save it for a post-purchase or lull send.
- 5. **Make the "Selling Fast" module specific** — "Sold 214 today" or naming a specific trending item would convert better than the vague current copy.

- **Subject Alt B:** `70% off. Ends Sunday.`
- **Preheader Alt A:** `We've never gone this low — shop before it's gone`
- **Preheader Alt B:** `Prices from £4. This is the bottom of the sale.`

### 3. Rendering & Accessibility

**`font-display: swap` on `@font-face`**
```css
font-display: swap;   /* appears in both FuturaPT-Book and FuturaPT-Heavy declarations */
```
Web-only CSS property — ignored by every email rendering engine. Harmless but indicates web CSS was copied without email adaptation.

**Web font support gap**
`FuturaPT-Book` / `FuturaPT-Heavy` loaded from `images.asos-media.com`. Web fonts fail silently in Outlook (all versions), Gmail (Web/Android/iOS), and Yahoo Mail — which together represent the majority of opens. The `mso-font-alt: Arial` and `font-family: ..., Arial, sans-serif` fallback stacks are correctly declared, so the fallback chain appears sound.

**`font-size: 0em` on table elements — silent text suppression risk**
```css
table, tr, td, th { font-size: 0em; }
```
Standard whitespace-gap fix, but any `<td>` that doesn't explicitly override `font-size` will render its text invisible. Must confirm every content cell in the body has an explicit `font-size` property.

**Mobile breakpoint at 460px — too narrow**
```css
@media screen and (max-width:460px) { ... }
```
De facto standard is 480px. Devices reporting viewport widths of 461–479px (e.g., some Android devices) won't trigger the mobile layout and will receive the desktop table layout instead.

**CSS ticker animation — broad client incompatibility**
```css
@keyframes ticker { ... }
@supports (animation: ticker 5s linear infinite) {
  .fallback { display: none !important; }
  .ticker   { display: block !important; }
}
```
`@keyframes` / `animation` unsupported in Outlook (all), Gmail Web, Gmail Android, Samsung Mail. The `@supports` fallback toggle is correctly implemented — non-supporting clients see `.fallback`, supporting clients see `.ticker`. No fix needed, but confirm `.fallback` content is fully self-contained and not dependent on `.ticker` being visible.

**Duplicate charset declaration**
```html
<meta http-equiv="Content-Type" content="text/html; charset=UTF-8">
<meta charset="utf-8">
```
Both present. Not harmful, but redundant — one should be removed to avoid ambiguity in strict parsers.

**`-webkit-font-smoothing` on `*`**
```css
* { -webkit-font-smoothing: antialiased !important; }
```
Overly broad selector; applies smoothing to non-text elements. No functional breakage, but the `!important` makes it difficult to override in any component that intentionally opts out.
