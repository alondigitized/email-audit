# Up to 25% extra off all Sale
**Score:** 8/10 · **Type:** Email audit · **2026-06-28**
## Executive summary

- This is ASOS's fourth sale escalation in six days — June 22 launched at 60% off, June 24 stacked an extra 10%, June 25 refreshed with new brands, and now June 28 swings another "25% extra off." The offer is objectively bigger than the June 24 send (25% vs. 10%), so there's a real reason to exist. The red hero banner is sharp, the dual-CTA layout is clean, and the "YOU'D LOOK GREAT IN THESE" personalization block is the most interesting new element ASOS has introduced in this run.
- The problem is cadence exhaustion. Any engaged subscriber who opened all four emails is now numb to the escalation loop. The fact that this lands on a Saturday, with a Monday deadline, is smart timing — weekend browse-to-buy is high. But the creative is structurally identical to the June 24 send: same hero, same red-on-white treatment, swapped percentage. There's no visual freshness to signal "this one is different."
- The combined-savings messaging ("Save 65%!") in the fine print below the code is doing real work but is too buried. The math is also slightly off — 25% extra off an already-60%-off item yields ~70% total, not 65% — which makes it feel slightly undersold or imprecise, depending on which way you read it.

## What's working

- **Red hero with stacked headline** stops the eye immediately — "UP TO 25% EXTRA OFF ALL SALE" reads in under a second.
- **Dual CTAs ("SHOP WOMEN'S" / "SHOP MEN'S")** respect both audience splits without diluting the headline offer.
- **Monday deadline** creates genuine weekend urgency; Saturday drop with a Monday close is textbook close-the-loop timing.
- **"YOU'D LOOK GREAT IN THESE"** implies behavioral personalization — the strongest new signal in this sale campaign if it's real.
- **Brand logo grid ("SHOP OUR TOP BRANDS")** echoes the June 25 new-brands-in-sale angle and gives a reason to browse beyond the hero offer.

## What's weak

- **Fourth sale email in six days** — cadence fatigue is real; a subscriber who bit on June 22 at 60% off already bought; one who passed on June 24's extra 10% may not be persuaded by a bigger discount from the same template.
- **"Save 65%!" in the fine print** — the math doesn't hold cleanly against the advertised stack (25% off a 60%-off price = ~70% total savings), making the headline offer feel vague.
- **Lifestyle editorial photos are generic** — the three large images in the "YOU'D LOOK GREAT IN THESE" block show models but no product names, prices, or clickable hooks; it's dead visual space on mobile.
- **Code visibility is weak** — the promo code sits in very small text below the hero; a subscriber skimming on mobile will miss it and may feel the discount doesn't apply when they reach checkout.
- **No social proof anywhere** — the June 22 launch earned the right to show "bestsellers this week" or "trending in sale," but this email doesn't use the accumulated sale data.

## Recommendations

- 1. **Make the code unmissable** — pull the promo code into the hero block at a readable size, styled like a coupon chip. Buried fine print kills conversion at checkout.
- 2. **Replace one lifestyle image with a specific product** — a single hero product with a "was $120, now $18" price callout (possible at 60%+25% off) would be more compelling than three anonymous editorial shots.
- 3. **Rewrite the combined-savings callout** — "Stack 25% extra on top of 60% off = up to 70% total savings" is truer, cleaner, and more impressive than "Save 65%!".
- 4. **Add urgency to the brand logo section** — "Brands selling fast in Sale" makes the browser-brand grid feel like scarcity, not just navigation.
- 5. **Break the visual template** — after four red-hero sale emails, a color swap (black/gold for final-hours mode) signals to subscribers that this is genuinely the last call, not another loop of the same drum.
- **Subject Alt A:** `"Ends Monday: 25% extra stacked on 60% off"`
- **Subject Alt B:** `"Up to 70% off when you use CPXX — ends Monday"`
- **Preheader Alt A:** `"Your wishlist is cheaper now than it'll ever be this summer."`
- **Preheader Alt B:** `"The code works on everything in Sale. Goes midnight Monday."`

### 3. Rendering & Accessibility

**Issue — `-webkit-text-size-adjust: none` on `body`:**
```css
body, #body_style {
  -webkit-text-size-adjust: none;
  -ms-text-size-adjust: none;
}
```
Setting to `none` prevents iOS from scaling text when the user has a larger preferred font size. Recommended value is `100%`, which prevents browser auto-scaling while still respecting user accessibility settings. This also appears a second time as `* { -webkit-text-size-adjust: 100%; }` — the `body` rule takes precedence, making the wildcard redundant and the `none` value the effective one.

**Issue — Global link underline removal:**
```css
a, span { text-decoration: none; color: inherit; }
```
Removes all visual link differentiation. Violates WCAG 1.4.1 (use of color alone to convey meaning). CTAs styled as buttons are exempt if they have sufficient contrast, but inline text links are not distinguishable from surrounding copy.

**Issue — Responsive breakpoint gap at 460px:**
```css
@media screen and (max-width:460px) { ... }
```
Standard email breakpoint is 600px. Devices with viewports between 461–599px (many Android phones in landscape, small tablets) render the desktop layout. If the desktop layout is fixed at 600px, it will overflow or require horizontal scroll on these viewports.

**Issue — `font-size: 0em` on all table elements:**
```css
table, tr, td, th { font-size: 0em; }
```
Standard ghost-whitespace fix, but any text placed directly inside a `<td>` without a wrapping `<p>` or `<span>` will be invisible. Confirm all body copy is wrapped in block elements.

**No issue — VML conditional comments:** Correctly scoped to `[if gt mso 15]` and wrapped in `<noscript>` per current best practice.

**No issue — Font loading:** `font-display: swap` is set; multiple formats (woff2, woff, otf, ttf, svg) cover all clients. SVG format is legacy-only and adds negligible weight but causes no harm.

**No issue — `lang="en"` on `<html>`:** Present and correct.
