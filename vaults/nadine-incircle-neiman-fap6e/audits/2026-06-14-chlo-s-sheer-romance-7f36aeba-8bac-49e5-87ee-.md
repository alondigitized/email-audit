## Technical Audit — Neiman Marcus "Chloé's sheer romance"

### 1. Technical Summary

The email is a standard Salesforce Marketing Cloud AMPscript build with functional mobile responsive CSS, but has three meaningful infrastructure gaps: unresolvable merge-token ambiguity in the AMPscript header, missing RFC 8058 one-click unsubscribe headers (a Gmail/Apple Mail compliance requirement as of 2024), and unverifiable SPF/DKIM authentication status due to the AgentMail relay stripping delivery headers.

---

### 2. Link & Tracking Issues

**36 tracking links skipped — zero HTTP-probed**
All click-redirect links (likely `click.e.neimanmarcus.com` or similar) were excluded from HTTP probing. Destination URL integrity, UTM coverage, and redirect chain health are entirely unverified for this send.

**Plain-text version is 86% URLs by character count**
QA flagged 3,098 of 3,594 plain-text chars as URLs. This ratio is abnormally high — a well-formed plain-text fallback should summarize content in human-readable prose with a handful of links. Spam filters (SpamAssassin, Gmail's classifier) penalize plain-text bodies that are URL-dense. This suggests the plain-text was machine-generated directly from href attributes rather than authored.

**Evidence:** QA finding: `Plain-text is >70% URLs: 3098/3594 chars are URLs`

---

### 3. Rendering & Accessibility

**`maximum-scale=1` on viewport meta blocks pinch-zoom**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">
```
This prevents users from zooming in on text. WCAG 1.4.4 (Resize Text, Level AA) requires content to be resizable up to 200% without assistive technology. iOS 10+ ignores this flag in Safari, but it still affects some Android WebViews.

**Three commented-out viewport metas are dead weight**
```html
<!--<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no" />-->
<!--<meta name="viewport" content="width=320, initial-scale=0.29">-->
<!--<meta name="viewport" content="width=1024">-->
```
These are vestigial from prior template iterations and should be deleted. They carry no rendering risk in-comment but indicate the template hasn't been cleaned up and could be accidentally re-enabled.

**CSS split across two `<style>` blocks with overlapping breakpoints**
Block 1 targets `max-width: 600px`; Block 2 targets `max-device-width: 480px` and `max-width: 480px`/`520px`. The dual-block pattern is functional but doubles the parse surface and makes cascade order non-obvious. The `max-device-width` descriptor is deprecated in CSS3 — `max-width` alone is the correct modern form.

**Hamburger nav uses CSS checkbox hack with no JS fallback**
The interactive nav relies on `:checked` pseudo-class state on a hidden `<input>`. This works in Gmail (CSS-only) but fails silently in clients that strip `<input>` elements (Outlook desktop, some enterprise webmail). No `<noscript>` or fallback nav is visible in the truncated source.

**`<title>` tag has a trailing space**
```html
<title>Neiman Marcus </title>
```
Minor, but some email clients surface the `<title>` in preview panes. Should be trimmed.

### 4. Personalization & Merge Tokens

**Ambiguous `@user` variable — scenario selection is uncommented but unresolved**

The AMPscript comment block states "CHOOSE ONE SCENARIO BELOW" and then shows exactly one scenario — but it is commented out:
```
<!--/* SET @user = HASHED_EMAIL_SHA256 */ -->
```
Above the comment, `@user` is defined as a Lookup against `NM_Subscriber_New_Consolidated` returning `EMAIL_ID`. The comment suggests a second scenario (hashed email for identity/ad matching) was intended to be wired in but was not. If `@user` is consumed downstream (e.g., passed to a data layer or tracking pixel), the wrong value may be flowing.

**`@refid` is a no-op CONCAT**
```
@refid = CONCAT(@base_refid,"")
```
Concatenating with an empty string does nothing. This is either a template stub that was never completed (e.g., it should append a suffix like `"_NM_EMAIL"`) or it's intentional padding. Either way, it's dead code that should be resolved or removed to avoid confusion.

**Multiple DE lookups on every open**
Four separate `Lookup()` calls hit two different Data Extensions (`NM_Subscriber_New_Consolidated`, `NM_CRM_Feed`) on render. At high volume this is a known SFMC performance bottleneck — lookup-heavy templates can contribute to slow render queues. Consider consolidating into a single joined DE if not already done.

### 5. Compliance

**`List-Unsubscribe` header absent — Gmail bulk sender requirement**
As of February 2024, Gmail requires bulk senders (>5,000/day) to include `List-Unsubscribe` headers. The AgentMail relay did not surface this header. If the ESP is setting it and the relay is stripping it, that is a relay configuration issue. If the ESP is not setting it, this is a compliance gap.

**`List-Unsubscribe-Post` (RFC 8058) absent — one-click unsubscribe not supported**
Gmail and Apple Mail use this header to enable one-click unsubscribe in the UI. Its absence means subscribers must navigate to a landing page to unsubscribe, which increases friction and complaint rates. Gmail treats the absence of RFC 8058 as a signal to surface its own unsubscribe prompt, which can suppress your sender reputation metrics.

**SPF/DKIM authentication status unknown**
```
Authentication-Results header not found: Expected via AgentMail relay — SPF/DKIM status unknown
```
The relay is not forwarding authentication results. Without confirmed DKIM pass on `e.neimanmarcus.com`, deliverability to Gmail and Yahoo cannot be assured. This needs to be verified at the MTA level, not the relay level.

**CAN-SPAM physical address and unsubscribe mechanism** — Cannot verify from truncated HTML. The footer is not included in the provided source. Assumed present but unconfirmed.

Because every outbound link passes through a click-redirect domain, no destination URLs, UTM parameters, or landing page states could be probed. The following cannot be confirmed:
